# The browser extension lock

2026-09-12. StayFree was found switched off in Zen, the browser in daily use, with
nothing on the machine able to notice or undo it.

## What was actually in place

`ExtensionInstallForcelist` in two root-owned Chromium managed-policy files, restored
every 60s by the watchdog:

    /etc/chromium/policies/managed/nightguard.json
    /etc/brave/policies/managed/nightguard.json

That is the whole of it. The Gecko half existed as a staged file,
`/var/lib/nightguard/policies/firefox-policies.json`, holding a correct-looking
`ExtensionSettings` force-install for the AMO add-on id. No code read it, `deploy.sh`
did not install it, `nightguard_watchdog.py`'s `POLICY_PATHS` did not name it, and
nothing restored it. It had been sitting there since 2026-06-22.

Confirmed state before the fix:

| Browser | StayFree |
|---|---|
| Chromium | force-installed, location 7 (external policy download) |
| Brave | force-installed, location 7 |
| Chrome | not installed at all — no policy file in `/etc/opt/chrome/policies/managed/` |
| Zen | ordinary add-on, `"active": false` in `extensions.json` |
| Firefox | ordinary add-on |

A policy file nothing reads is indistinguishable from one that works. That is the
failure mode this document exists to close, and why the fix ships with a probe rather
than a checklist.

## Where a Gecko policy has to live

Firefox forks read `<SysConfD>/policies/policies.json` FIRST and, when it exists, never
read the install-directory copy — `EnterprisePoliciesParent._getLocalConfigurationFile`
returns the system file early. `SysConfD` on Linux is `/etc/<MOZ_APP_NAME>`. Read off
the shipped builds on this box:

    /opt/zen-browser-bin  MOZ_APP_NAME "zen"      MOZ_SYSTEM_POLICIES true
    /usr/lib/firefox      MOZ_APP_NAME "firefox"  MOZ_SYSTEM_POLICIES true

So the targets are `/etc/zen/policies/policies.json` and
`/etc/firefox/policies/policies.json`. Neither directory existed — which is why the
staged file had nowhere to land even if something had tried to install it.

Because the system file SHADOWS the vendor's, writing the lock naively would have
silently dropped Zen's own `DisableAppUpdate` and `DefaultSerialGuardSetting`, and
Firefox's Arch `Preferences` block. The watchdog therefore reads the install-directory
file every tick and merges the lock on top, so a package update propagates instead of
being frozen at deploy time.

## What is enforced now

Five files, all root-owned, all regenerated by the watchdog every 60s:

    /etc/chromium/policies/managed/nightguard.json
    /etc/brave/policies/managed/nightguard.json
    /etc/opt/chrome/policies/managed/nightguard.json      (new)
    /etc/zen/policies/policies.json                        (new)
    /etc/firefox/policies/policies.json                    (new)

### The ways a browser starts WITHOUT the extension

Force-installing stops the add-on being disabled or removed. It does not cover the
sessions the add-on is not in, and each family closes those differently.

| Hole | Chromium family | Gecko family |
|---|---|---|
| Private / incognito window | no policy grants an extension incognito access — `ExtensionSettings` has no incognito key — so the only enforcement is `IncognitoModeAvailability: 1`, removing the feature | `private_browsing: true` on the extension's entry, so the add-on runs in private windows and private browsing stays usable |
| A clean profile with no extensions | `BrowserGuestModeEnabled: false` — a guest session carries no extensions and no toggle to lose | `DisableSafeMode: true` — safe mode starts with every extension off, two clicks from the help menu |
| A brand-new profile | covered: machine-wide managed policy applies to every profile | covered: the policy is install-wide |

`private_browsing` is absent from this build's `policies-schema.json`, but the runtime
reads it: `Extension.sys.mjs._setupStartupPermissions` calls
`Services.policies.getExtensionSettings(id).private_browsing` and grants or revokes
`internal:privateBrowsingAllowed` from it. It survives validation because the schema
describes no concrete extension ids at all — it declares only the literal `"*"`
property and no `patternProperties`, so `PolicySchemaValidator` passes an id's settings
object through unvalidated and unstripped.

The asymmetry is deliberate: Chromium can only close incognito by deleting it, Gecko
can hand the add-on the private window instead. Each browser gets the strongest lock it
actually supports.

## Proving it, rather than asserting it

    python3 /usr/local/lib/nightguard/verify_browser_lock.py

Three checks. Every policy file present, root-owned, owner-unwritable and
byte-identical to what the watchdog would write; each Gecko browser started headless
against a throwaway profile to read back WHICH `policies.json` it actually used; and
the Chromium profiles' `location` marker, which reads 7 only when a managed policy
installed the extension.

The second check is the one the old setup would have failed, and it is what makes this
evidence rather than configuration.

### Getting the policy path out of Gecko

The policy engine logs its path at debug through `ConsoleAPI`. Reaching the process's
stdout needs THREE prefs, and the missing third is silent. Measured on this box:

| Prefs set | Result after 50s |
|---|---|
| `browser.policies.loglevel=debug`, `devtools.console.stdout.chrome=true` | 2181 bytes of other console output, no policy line |
| the same plus `browser.dom.window.dump.enabled=true` | `policies.json path = ...` every run |

Without the third pref the probe reads exactly like a browser that never looked for a
policy file — the same false negative the original hole hid behind.

## What this still does not stop

- **Root.** The owner has `(ALL) ALL` with a password. Everything here is root-owned
  files restored on a 60s timer: it costs a password and survives at most 60 seconds,
  which is friction, not a wall. That is the same bargain the rest of the guard makes.
- **A browser nobody thought of.** The lock is per-installed-browser. Installing
  LibreWolf, Floorp, Vivaldi or Opera gets an unlocked browser until its policy target
  is added to `POLICY_PATHS` or `MOZILLA_POLICY_TARGETS`.
- **Uninstalling StayFree's job.** The extension's own schedule decides what is blocked
  when. This layer only guarantees it is running.
