### Locked Decisions

**D-01: `pkexec`/polkit replaces `sudo` on a PTY, and this was proven live on this box, not assumed.** Test sequence and evidence:
- `pkexec whoami` (no PTY) returned root after a real graphical auth dialog. The user confirmed seeing and authorizing it (password, since the fingerprint sensor was wedged at the time — see the fingerprint-hardware finding below (D-02)). `journalctl` showed a genuine `polkit-agent-helper` session and `pam_unix(polkit-1:session): session opened for user root` each call — not a cache hit.
- Two back-to-back `pkexec` calls each triggered a **fresh** PAM session (new `polkit-agent-helper` PID, new D-Bus unique name each time) — confirms `implicit any: auth_admin` (from `pkaction --action-id org.freedesktop.policykit.exec -v`) does NOT retain/cache, matching the anti-impulse requirement that `sudo -k` currently provides (there is no `-k` equivalent needed for `pkexec` — it never caches under this action).
- Dry-run of the **exact** invocation shape `backend.commit()` uses today — swap `sudo -k` for `pkexec`, drop the PTY entirely: `pkexec /usr/bin/python3 /usr/local/lib/nightguard/nightguard_ctl.py verify` (the `verify` subcommand used as a safe stand-in for `commit`) — completed through a real auth dialog with no PTY involved.
- **No system files were installed** for this proof (no custom polkit `.policy` action) — the test used polkit's built-in `org.freedesktop.policykit.exec` action, which is what plain `pkexec <program>` invokes. Whether the phase's implementation defines its own scoped action (recommended, so the authorization prompt names Nightguard specifically rather than "run a program as another user") is a planning-time decision, not a gate question — the mechanism itself is proven either way.
- Omarchy's own polkit agent (`/usr/share/omarchy/shell/plugins/polkit/PolkitAgent.qml`) is what answers the prompt — no new agent needs to be written. It reads `/etc/pam.d/polkit-1` to detect a fingerprint-configured stack, exactly mirroring `backend.commit()`'s own comment about "fingerprint first" — because it is the same physical PAM configuration (`pam_fprintd.so sufficient` then `pam_unix.so required`) as `/etc/pam.d/sudo`, just reached through polkit's D-Bus flow instead of a TTY.

**D-02: Fingerprint auth itself did not verify end-to-end on this box during testing — a hardware/driver issue, not a gate blocker.** The "Elan MOC Sensors" device raised `fpi_ssm_mark_failed: assertion 'machine != NULL' failed` in `fprintd`'s own driver state machine and repeatedly denied claims ("Device was already claimed") independent of anything nightguard-related — the condition predated this session's first test. Restarting `fprintd.service` cleared stuck claims temporarily but the assertion recurred. The user confirmed live: *"the fingerprint sensor doesnt work properly"* — touched the sensor, nothing registered. This affects `sudo`'s fingerprint path identically (same PAM stack, same physical sensor) — it is not a regression introduced by moving to polkit, and is out of scope to fix in this phase. Password-based polkit auth is proven; fingerprint should be re-verified once the sensor itself is working, but is not a blocker to building the panel.

**D-03: `nightguard_ctl.py` (the root signer script, pinned at `/usr/local/lib/nightguard/nightguard_ctl.py` via `_resolve_stack_dir()`) is "the backend" that stays the sole writer/signer.** The panel calls it exactly as the terminal app did — same pinned-path resolution, same argv shape (`/usr/bin/python3 <CTL_SCRIPT> commit --from <tmp>`), same content-via-tempfile (never on the command line). Only the outer wrapper changes: `pkexec` instead of `sudo -k` on a PTY, and none of the PTY/ANSI/auth-chatter filtering (`_run_sudo_pty`, `_split_commit_output`, `_AUTH_NOISE`) is needed — polkit's own agent owns the dialog entirely out-of-process, so the caller only ever sees the CLI's own stdout/stderr and exit code.

**D-04: `ngtui/ngtui/backend.py` and its pinned-path validation SURVIVE the terminal app's retirement** — only the Textual layer (`app.py`, screens, widgets — everything importing `textual`) is deleted at the retirement step. `backend.py` already holds zero Textual imports; it is a pure library over the trust stack (`ngcommon`, `guard`, `nightguard_ctl`) that computes preview/classify/quota exactly as the signer will. Keeping it means one pinned-path resolution, one classifier/quota code path — not two implementations of the same trust-critical logic.

**D-05: The existing `ngtui` CLI argv router gains two non-interactive subcommands, called by the panel via `Process` exactly like the two it already has (`ngtui status --json`, `ngtui panel`):**
- `ngtui preview --from <path>` — unprivileged, wraps `backend.preview_change()`; prints the direction labels + quota decision (cost, refusal reason, loosening/tightening) as JSON so the panel can show cost/refusal **before** any authentication, per BLK-04.
- `ngtui commit --from <path>` — thin: builds `["pkexec", "/usr/bin/python3", CTL_SCRIPT, "commit", "--from", tmp]` and runs it via plain `subprocess.run` (no PTY, no output-scrubbing needed). Exit code + stdout/stderr pass straight through.
This keeps the panel's `Process` calls uniform with what `BarWidget.qml` already does, and keeps the pinned-path/validation logic in exactly one place through the transition.

**D-06: Inline editing within the existing scrollable panel column, not popup-per-field.** Matches the first-party idiom in `monitor`/`network` panels and the shell's own component set: `ToggleSwitch` for app mode, `Toggle` for game blocking, `TextField` + a removable row list for the site blocklist and the allowlist. Edits stage locally in the panel (no signer call yet) exactly as the terminal editor staged them. A single `PanelActionButton` commits all staged changes; a `ConfirmDialog` gates the actual commit, showing the token cost and the direction (loosening/tightening) computed by `ngtui preview` — so cost and any refusal are visible before the `pkexec` dialog ever appears, never after.

**D-07: Full BLK-01..05 parity, including BLK-03's informational surface** (process-match highlighting, detected game titles, the allowlist floor, cgroup-vs-SIGTERM enforcement strength) **is the retirement bar**, not a "core actions first" cut. ## Summary

This is not a greenfield phase and it is not mostly a UI phase. The UI contract is already written (`12.2.1-UI-SPEC.md`, 740 lines, every component read off disk) and the authorisation mechanism is already proven live (CONTEXT D-01). What research found instead is that **three things between the panel and the signer are broken or missing today**, and every one of them was proven by running code rather than by reading it:

1. **`lineedit.list_add` cannot add the first entry to `blocking.browser_extension.blocked_urls`.** The live value is the flow-style empty list `blocked_urls: []`; `list_add` appends a block-style `- item` line underneath it, and `ngcommon.yaml_load` then dies with `AttributeError: 'dict' object has no attribute 'append'`. BLK-01's headline key is unreachable until this is fixed. Reproduced end-to-end below.
2. **The CLI surface in D-05 cannot be implemented as literally written.** `ngtui preview --from <path>` takes a *proposed config file*, which means the caller must produce format-preserving edited YAML. QML cannot do that, and a re-emit is explicitly forbidden (STATE 10-03, T-10-09: a re-emit changes the bytes the signer HMACs, so the guard reverts the user's own commit). The CLI must take **staged ops**, not a proposed document, so that `lineedit.py` stays the single composition path.
3. **Moving from `sudo` to `pkexec` re-opens a bypass that `sudo` was immune to, and silently drops a chown.** `/usr/share/polkit-1/rules.d/empower.rules` returns `polkit.Result.YES` for *every* action for any member of the `empower` group — with `sudo` that group meant nothing; with `pkexec` it means the commit gate disappears entirely, with no prompt. Separately, the signer's `_chown_back_config()` reads `SUDO_UID`, which `pkexec` does not set (it sets `PKEXEC_UID`), so after the first pkexec commit `config.yaml` flips from `danitrrga:danitrrga` to `root:root` and the hand-edit-then-revert model that `deploy.sh` deliberately preserves stops working.

Everything else is favourable. The polkit primitives are all verified on this box: `pkexec` 126/127 exit codes from its own man page, custom `.policy` actions readable from `/usr/local/share/polkit-1/actions` (polkit 126+ feature, confirmed two ways), `auth_admin` semantics, and — critically — a **non-interactive** authorisation probe (`pkcheck` without `-u`) that proves the gate is real without ever popping a dialog. The QML side has a machine-checkable seam that is already live: `qs -p /usr/share/omarchy/shell/shell.qml ipc call danitrrga.nightguard state` returns the widget's computed state as JSON right now.

**Primary recommendation:** Plan Wave 0 as three repair tasks — fix `lineedit.list_add` for flow-style empty lists, make `_chown_back_config()` pkexec-aware, and add an `AUTH_ADMIN` rule for the nightguard action to `/etc/polkit-1/rules.d/00-nightguard.rules` so the `empower` blanket YES can never reach it — then build the panel against an **ops-based** CLI (`ngtui preview --ops <json>` / `ngtui commit --ops <json>`) so `lineedit.py` remains the one and only place a config edit is composed.

## Blockers found live — fix these before the panel is built

Each was reproduced by executing code on this box on 2026-09-13, with the verbatim output recorded.

### B-1 — `lineedit.list_add` produces invalid YAML on `blocked_urls: []` (blocks BLK-01)

The live sanctioned config (`/var/lib/nightguard/config.sanctioned.yaml`) has:

```yaml
    blocked_urls: []
```

`lineedit.list_add` (`ngtui/ngtui/lineedit.py:192-205`) falls back to `item_indent = key_indent + 2` when `_list_block_bounds` finds no existing items, and inserts the item **after** the key line without touching the `[]`:

```yaml
    blocked_urls: []
      - youtube.com
```

Feeding that to the signer's own parser:

```
AttributeError: 'dict' object has no attribute 'append'
  File ".../scripts/linux/ngcommon.py", line 181, in parse_block
    result.append(_scalar(content))
```

**Consequence:** `backend.preview_change()` raises, so the first blocked URL can never be added. The existing TUI fails closed (`edit.py:_stage` catches `Exception` and rejects the keystroke), which is why this was never seen as a crash — it was seen as "the site list just doesn't work". The new panel must fail closed identically **and** the underlying op must be fixed, or BLK-01's headline key is undeliverable.

**Fix shape:** when `item_indent == -1` *and* the key line's value is a flow-style empty collection (`[]`), rewrite the key line to `key:` (dropping the `[]`, preserving indentation and any trailing comment) before inserting the item. `_rebuild_scalar_line` / `_split_value_comment` already exist for exactly this kind of surgery.

**Measured behaviour of the three ops that do work** (so the planner does not re-test them):

| Op | Key | Result |
|---|---|---|
| `list_add` | `blocking.native_apps.allowlist` (block-style, 2 items) | `['zen-bin', 'foot', 'ghostty']` ✅ |
| `list_remove` ×2 → empty | `blocking.native_apps.allowlist` | key line remains `    allowlist:`; parses to **`None`, not `[]`** — the classifier handles it (`_compare_lists` does `list(new or [])`), but the panel must render `None` as empty ✅ with a caveat |
| `set_scalar` | `blocking.native_apps.mode` → `allowlist` | `'allowlist'` ✅ |
| `toggle_bool` | `blocking.native_apps.block_games` → true | `True` ✅ |

### B-2 — the `empower` group is a total bypass of the commit gate under pkexec (PANEL-01)

`/usr/share/polkit-1/rules.d/empower.rules`, verbatim:

```javascript
// Allow all actions for users who are in the "empower" group. Users are added to the
// "empower" group by running run0 --empower.
polkit.addRule(function(action, subject) {
    if (subject.isInGroup("empower")) {
        return polkit.Result.YES;
    }
});
```

Current state, verified: `getent group empower` → `empower:x:997:` (**empty** — not currently live). `id` → `danitrrga` is in `wheel` (998) but not `empower`.

Under `sudo`, membership in `empower` meant nothing — sudo does not consult polkit. Under `pkexec`, one `run0 --empower` makes every nightguard commit succeed **with no prompt at all**. That is the anti-impulse guarantee evaporating, silently, via a command the user already has.

The project already half-knows this: `ngtui/ngtui/panel.py:353-362` (`empower_warning`) documents it exactly — *"after which every polkit action returns YES with no prompt"* — and `__main__.py:_live_warnings()` surfaces it. But a warning in the panel is detection, not prevention, and it was written when only the watchdog-stop action was at stake.

**Structural fix, verified possible:** `man 8 polkit` on this box states *"Functions are called in the order they have been added until one of the functions returns a value"*, and rule files are processed in lexical order by basename with `/etc` winning ties. `/etc/polkit-1/rules.d/00-nightguard.rules` **already exists** and already sorts ahead of `empower.rules`. Adding a branch that returns `polkit.Result.AUTH_ADMIN` for the nightguard exec action makes the `empower` YES structurally unreachable for this action — the first rule to return a value wins, and ours runs first.

This requires the scoped `.policy` action (so there is an action id to match on), which converts the Claude's-Discretion item into a near-requirement.

### B-3 — `pkexec` does not set `SUDO_UID`, so `config.yaml` flips to `root:root` (PANEL-01)

`nightguard_ctl.py:477-483`:

```python
def _chown_back_config():
    uid, gid = os.environ.get("SUDO_UID"), os.environ.get("SUDO_GID")
    if uid and gid:
        try:
            os.chown(ng.CONFIG, int(uid), int(gid))
```

`man pkexec` (this box): *"the `PKEXEC_UID` environment variable is set to the user id of the process invoking pkexec"* — there is no `SUDO_UID`. So the guard clause is false, the chown is skipped, and `_atomic_write_bytes` (mode `0o644`, running as root) leaves `/var/lib/nightguard/config.yaml` owned `root:root`.

Current live state: `-rw-r--r-- danitrrga danitrrga config.yaml`. `deploy.sh` sets this deliberately and says why:

> `# config.yaml stays the user's to edit in place — the revert model needs the hand edit to be possible so the watchdog can undo it.`

The parent directory is `root:root 0755`, so once the file is root-owned the user cannot edit it, cannot recreate it, and cannot rename it aside. The watchdog's demonstrated "hand-edit silently reverts" behaviour — one of the two halves of the project's core value statement — becomes untestable and, for the user, gone.

**Fix shape:** read `PKEXEC_UID` when `SUDO_UID` is absent, deriving the gid via `pwd.getpwuid(uid).pw_gid`. One function, plus a `deploy.sh` run and a test. Note this edits the **root signer**, so `scripts/linux/nightguard_ctl.py` must change *and* `deploy.sh` must be re-run — editing the repo alone changes nothing that root executes.

### B-4 — `deploy.sh` never installs `NightguardPanel.qml`

`deploy.sh` installs the plugin with an explicit two-file loop:

```bash
for f in manifest.json BarWidget.qml; do
```

`NightguardPanel.qml` is absent from it. The live copy at `~/.config/omarchy/plugins/danitrrga.nightguard/NightguardPanel.qml` is dated Sep 7 21:32 and happens to be `diff`-identical to the repo today — by hand, not by deploy. This phase makes `NightguardPanel.qml` the file that changes the most, so the gap goes from cosmetic to load-bearing: an executor could edit the repo, run deploy, and be testing the *old* panel.

There is already a test guarding the analogous gap for the Python stack (`ngtui/tests/test_deploy_completeness.py`, written because `appblock.py` was exactly this bug). The same shape extends to the plugin file list.

## Architecture Patterns

### System architecture — the commit path end to end

```
  user edits a row in the panel
        │
        ▼
  [QML]  staged ops list  ──────── staged locally, no signer call
   [{op,key,value}, ...]           (removal stays visible + dimmed; addition appended with a direction marker)
        │
        │ on every stage/unstage (NOT on the poll tick)
        ▼
  Process: ngtui preview --ops /tmp/ops.json
        │
        ├─► [CLI] read backend.sanctioned_text()          ← the SIGNED bytes, the only base
        ├─► [CLI] replay ops through lineedit.*           ← format-preserving; the ONE composition path
        ├─► [CLI] backend.preview_change(proposed_text)
        │        └─► imports nightguard_ctl.classify_change  → dirs   [(label, loosen|tighten|noop)]
        │            imports nightguard_ctl.quota_decide     → decision {allowed, costs_token, reason, effective_spent}
        │            (clock read via backend.cache_only_now_minutes — no synchronous network query)
        └─► stdout: one JSON line {ok, dirs, loosening, decision}
        │
        ▼
  [QML] render per-row direction + total cost + any refusal
        │
        │  decision.allowed === false  ──────────────► commit button enabled:false, reason on screen, STOP
        │  preview failed / unparseable ────────────► preview-unavailable line, commit disabled, STOP (fail closed)
        ▼
  user presses "Aplicar cambios"
        ▼
  ConfirmDialog (selectedIndex: 0 — cancel is the default)
        ▼
  Process: ngtui commit --ops /tmp/ops.json
        │
        ├─► [CLI] recompose the SAME proposed text from the SAME ops   (never trust a client-supplied document)
        ├─► [CLI] write it to tempfile.mkstemp()  (0600, content never on a command line)
        └─► subprocess.run(["pkexec", "/usr/bin/python3", CTL_SCRIPT, "commit", "--from", tmp])
                                 │
                                 ▼
                    polkitd  ──► rules.d (00-nightguard wins over empower) ──► AUTH_ADMIN
                                 │
                                 ▼
                    Omarchy PolkitAgent.qml  ──► PAM (/etc/pam.d/polkit-1: fprintd sufficient → unix required)
                                 │
                     ┌───────────┼────────────┬──────────────┐
                 authorised   dismissed    not authorised
                     │           │               │
                     ▼          126             127
         [root] nightguard_ctl.py commit
             ├─ canonicalize(bytes)
             ├─ classify + quota_decide  ← re-decided under root, with LIVE true time
             ├─ REFUSED → exit 1, stderr "REFUSED (dir): reason"
             ├─ no-op   → exit 0, stdout "no-op: ..."
             └─ commit  → fd-lock: sanctioned → guard.json (re-signed) → config.yaml → chown back → audit
                          exit 0, stdout "committed (...): config_hmac=... | tokens n/3 used"
        │
        ▼
  [QML] result line, verbatim from the CLI; then re-read state. Never optimistic.
```

The signer re-classifies and re-decides under root with live NTP time. The preview is advisory and deliberately cache-only — a warm cache makes them agree, a cold one makes the preview refuse where the signer might allow. That asymmetry is correct (fail closed) and must not be "fixed".

### Pattern 1 — the ops-based CLI (supersedes D-05's `--from`)

**What:** Two new subcommands on the existing `ngtui` argv router that take a *staged ops document*, not a proposed config.

**Why not `--from <proposed-config>`:** the caller would have to produce format-preserving edited YAML. In QML that means either a JS YAML emitter (re-emit changes the signed bytes → the guard reverts the user's own commit, T-10-09) or a JS reimplementation of `lineedit.py`'s indentation-tracked dotted-path line editor (a second trust-critical code path — exactly what D-04 exists to prevent).

**Ops vocabulary** — already fixed by `lineedit.py` and `edit.py:_compose_text:547-559`, do not invent a new one:

```json
{"ops": [
  {"op": "toggle",      "key": "blocking.native_apps.block_games", "value": "true"},
  {"op": "set",         "key": "blocking.native_apps.mode",        "value": "allowlist"},
  {"op": "list_add",    "key": "blocking.native_apps.allowlist",   "value": "ghostty"},
  {"op": "list_remove", "key": "blocking.browser_extension.blocked_urls", "value": "youtube.com"}
]}
```

`value` is always a string; `toggle` compares `value == "true"`.

**Output envelope** — the panel must be able to tell "old shim" from "signer said no" from "preview failed":

```json
{"ok": true,  "dirs": [["curfew.enabled","noop"], ...], "loosening": false,
 "decision": {"allowed": true, "costs_token": false, "is_noop": false,
              "reason": null, "effective_spent": 0, "week_anchor": "2026-09-08"}}
{"ok": false, "error": "list entry not found: 'x' in 'blocking.native_apps.allowlist'"}
```

Parse-ability is checked before the exit code, because the exit-code space is crowded (below).

**Exit-code map the panel keys on** — three ranges that must not be conflated:

| Code | Source | Meaning | Panel copy (UI-SPEC §9.3) |
|---|---|---|---|
| 0 | signer | committed, or `no-op:` on stdout | `✓ aplicado — {stdout}` / `· sin cambios: …` |
| 1 | signer | `REFUSED (dir): reason` on stderr | `✕ rechazado — {última línea de stderr}` |
| 2 | signer | cannot read `.guardkey` | (same urgent treatment as 1) |
| **2** | **old `ngtui` shim** | stderr is exactly `ngtui must be run in a terminal (no TTY on stdin).` — **verified live** | `Detalle no disponible: el ngtui instalado no conoce «{subcomando}». Ejecuta el despliegue.` |
| 126 | `pkexec` | user dismissed the dialog | `✕ cancelado — no se autorizó nada, no se ha escrito nada` |
| 127 | `pkexec` | not authorized, or an error occurred | `✕ no autorizado — no se ha escrito nada` |

The exit-2 collision is real and was measured: an un-redeployed shim routes any unknown subcommand to `_run_tui()`, which on a non-TTY writes that line and raises `SystemExit(2)` (`ngtui/ngtui/__main__.py:44-46`). **Recommendation:** add an explicit unknown-subcommand branch to `main()` returning `64` (`EX_USAGE`) so future shims are unambiguous, and until then disambiguate on the stderr string. Do not let an old shim's exit 2 render as "the signer refused".

### Pattern 2 — the polkit scoped action

**Where it installs:** `/usr/local/share/polkit-1/actions/eu.tarraga.nightguard.policy`

Verified two ways that polkit reads this directory:
- `man 8 polkit` on this box diagrams four action directories: `/etc/polkit-1/actions`, `/run/polkit-1/actions`, `/usr/local/share/polkit-1/actions`, `/usr/share/polkit-1/actions`.
- polkit `NEWS.md` (upstream): version **126** added *"read actions also from /etc/, /run/ and /usr/local/share/ (Luca Boccassi)"*. This box runs **127**.

`/usr/local/share/` is the right choice: it matches the project's existing `/usr/local/lib/nightguard` convention for locally-installed, non-distro-packaged files, and it does not collide with a package-manager-owned directory. `/etc/polkit-1/actions` does not currently exist on this box and is for admin overrides, not for a project's own action definition.

**How pkexec selects it** — from `man pkexec`, ACTION AND AUTHORIZATIONS:

> By default, the `org.freedesktop.policykit.exec` action is used. To use another action, use the `org.freedesktop.policykit.exec.path` annotation on an action with the value set to the full path of the program. […] If the `org.freedesktop.policykit.exec.argv1` annotation is present, the action will only be picked if the first argument to the program matches the value of the annotation.

The program here is `/usr/bin/python3`, not the signer. **The `argv1` annotation is therefore mandatory, not optional.** The man page says so explicitly for exactly this case:

> Be careful to get the latter annotation right, otherwise it will match any pkexec invocation of `/usr/bin/python3` scripts.

Without `argv1`, any `pkexec /usr/bin/python3 <anything>` on the machine would be authorised under the nightguard action and would inherit whatever `<defaults>` it carries.

**`implicit_authorization` must be `auth_admin`** — never `auth_admin_keep`, never `yes`. `man pkexec`'s own SECURITY NOTES explain why this is not a style preference:

> Note that pkexec does no validation of the ARGUMENTS passed to PROGRAM. In the normal case (where administrator authentication is required every time pkexec is used), this is not a problem […] However, if an action is used for which the user can retain authorization (or if the user is implicitly authorized) this could be a security hole.

A `_keep` variant would also destroy the anti-impulse property directly: CONTEXT D-01 proved two back-to-back `pkexec` calls each open a fresh PAM session under `auth_admin`. That is the `sudo -k` equivalent, and it is what is being preserved.

**Admin identity** — `/usr/share/polkit-1/rules.d/50-default.rules` sets `adminIdentities` to `["unix-group:wheel"]`, and `danitrrga` is in `wheel` (gid 998, verified). So `auth_admin` prompts for the user's own password, not root's. If that ever changed, the dialog would ask for a root password the user may not have — worth a one-line note in the deploy output, not a guard.

**File shape:**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE policyconfig PUBLIC "-//freedesktop//DTD polkit Policy Configuration 1.0//EN"
 "http://www.freedesktop.org/software/polkit/policyconfig-1.dtd">
<policyconfig>
  <vendor>Nightguard Control</vendor>
  <action id="eu.tarraga.nightguard.commit">
    <description>Change the Nightguard curfew configuration</description>
    <description xml:lang="es">Cambiar la configuración del curfew de Nightguard</description>
    <message>Authentication is required to change your Nightguard curfew.</message>
    <message xml:lang="es">Hace falta autenticarse para cambiar tu curfew de Nightguard.</message>
    <defaults>
      <allow_any>auth_admin</allow_any>
      <allow_inactive>auth_admin</allow_inactive>
      <allow_active>auth_admin</allow_active>
    </defaults>
    <annotate key="org.freedesktop.policykit.exec.path">/usr/bin/python3</annotate>
    <annotate key="org.freedesktop.policykit.exec.argv1">/usr/local/lib/nightguard/nightguard_ctl.py</annotate>
  </action>
</policyconfig>
```

Action ids may contain only `[A-Za-z0-9.-]` (`man 8 polkit`). The file must be **named after the namespace** with a `.policy` extension.

`allow_gui` is deliberately **not** set: the signer is not an X11 program and the annotation is documented as discouraged.

**The rules.d half (closes B-2):** extend the existing `/etc/polkit-1/rules.d/00-nightguard.rules`, which already sorts first and already carries the `AUTH_ADMIN (not AUTH_ADMIN_KEEP)` rationale in its own header comment:

```javascript
polkit.addRule(function (action, subject) {
    if (action.id == "eu.tarraga.nightguard.commit") {
        return polkit.Result.AUTH_ADMIN;
    }
});
```

Because *"Functions are called in the order they have been added until one of the functions returns a value"* (`man 8 polkit`) and `00-nightguard.rules` in `/etc` sorts before `empower.rules` in `/usr/share`, this returns first and the blanket `YES` never runs for this action. This is the only construction that makes the guarantee structural rather than advisory.

**Deployment:** `deploy.sh` already has the install pattern (`install -d -o root -g root -m 0750 /etc/polkit-1/rules.d` + `install -o root -g root -m 0644 …`). The action file needs `install -d -o root -g root -m 0755 /usr/local/share/polkit-1/actions` and `-m 0644`. polkitd monitors both directory sets and re-reads on change — no daemon restart needed.

### Pattern 3 — the QML `Process` idiom for a write

Read off `BarWidget.qml` (read-only today) and `monitor/Panel.qml` (which does write):

```qml
// Reusable write Process: command assigned at call time, then running = true.
// Shape from monitor/Panel.qml:428-435 (actionProc).
Process {
  id: commitProc
  stdout: StdioCollector { waitForEnd: true }
  stderr: StdioCollector { waitForEnd: true }       // NEW — BarWidget has no stderr collector today
  onExited: function(exitCode, exitStatus) {        // menu/Menu.qml:982 signature
    root.applyCommitResult(exitCode, exitStatus,
                           commitProc.stdout.text, commitProc.stderr.text)
  }
}

// A Process still running cannot be relaunched — BarWidget.qml:153-156.
// Both new Processes need the same watchdog, and commit needs a LONGER one:
// pkexec blocks on a human at a dialog.
Timer { interval: 10000;  running: previewProc.running; onTriggered: previewProc.running = false }
Timer { interval: 120000; running: commitProc.running;  onTriggered: commitProc.running = false }
```

`exitStatus !== 0` means the process was killed by a signal rather than exiting — `menu/Menu.qml:984-986` documents the trap: *"A signal leaves the exit code at 0, so the status is what tells us."* A watchdog-killed commit must therefore never be rendered as a success.

**Do not call `refresh()` optimistically after a commit.** UI-SPEC §8.1 says re-read state; `monitor/Panel.qml:406-414` documents the opposite failure (re-reading races the hardware). Here the signer is authoritative and its stdout carries the new `config_hmac` and token count, so: render the verbatim result line, then trigger the existing `detailProc` re-read.

### Pattern 4 — `PanelKeyCatcher` + `TextField` + `ConfirmDialog`

`PanelKeyCatcher.qml:47` is `Keys.priority: Keys.BeforeItem` and line 49 is `if (blocked) return`. The catcher takes keys **before** descendants regardless of focus, so a `TextField` inside it receives nothing until `blocked: true`.

> **Stale comment warning.** `network/Panel.qml:990-992` claims *"AfterItem priority lets the passphrase TextField (a child via focus chain) get its keys first"*. That is **wrong** — the component hardcodes `BeforeItem` and the network panel actually works because of its `blocked: root.passwordSsid !== ""` line two lines below. Trust `PanelKeyCatcher.qml:47`, not the network comment.

The working idiom, copied from network (`Panel.qml:996`, `1840-1888`):

```qml
PanelKeyCatcher {
  id: keyCatcher
  blocked: root.editingEntry !== "" || confirmDialog.opened   // a STATE flag, never `field.activeFocus`
  ...
}

TextField {
  id: addField
  placeholderText: "añadir un sitio (p. ej. youtube.com)"
  onAccepted: root.stageAdd(addField.text)
  Keys.onEscapePressed: root.cancelEntry()
  onVisibleChanged: if (visible) Qt.callLater(forceActiveFocus)   // callLater, not direct
  Component.onCompleted: if (visible) Qt.callLater(forceActiveFocus)
}
```

`blocked` must be a state flag, not `activeFocus`: the catcher declares `focus: true`, so keying the gate off the field's own focus is a chicken-and-egg that leaves `j` scrolling the panel instead of typing.

`TextField` inherits QQC `TextField`, so `text`, `placeholderText`, `accepted`, `editingFinished`, `validator` are all available un-re-exposed (documented at `Ui/TextField.qml:5-8`). Mouse hover is read from the **inherited** `hovered` property via `onHoveredChanged` — the kit deliberately adds no `hovered(bool)` signal here because it would be shadowed (`TextField.qml:28-33`). That is the one component in the inventory whose hover wiring differs from the rest.

**ConfirmDialog inside a PanelKeyCatcher has no precedent** (UI-SPEC §6.4 — verified: the only two uses, `menu/Menu.qml:1119` and `clipboard/Clipboard.qml:400`, both live in surfaces with their own `Keys.onPressed` where `dialog.handleKey(event)` is the first branch). `handleKey` needs an `event` object the catcher's semantic signals do not carry, so route the signals instead, per UI-SPEC §6.4's table. Two additions research found that UI-SPEC's table does not list:

- `onDeleteRequested` (`x`) must **also** be swallowed while the dialog is open, or `x` removes a list entry behind an open confirm.
- `Key_Return` fires **both** `returnRequested()` and `activateRequested()` (`PanelKeyCatcher.qml:71-73`). If the panel wires both, Enter double-fires. Wire only `onActivateRequested`.

`ConfirmDialog` card width is `Math.min(parent.width - Style.space(32), Style.space(370))` (`ConfirmDialog.qml:51`) — at UI-SPEC's new `contentWidth: Style.space(380)`, it fits.

### Anti-patterns to avoid

- **Composing YAML in QML.** Any JS that emits or line-edits config text duplicates `lineedit.py` into a second trust-critical path. The edit-view port that established it (STATE 10-03) and its threat entry (T-10-09) are the recorded reason.
- **Classifying direction or computing cost in QML.** BLK-05 in one sentence. The panel renders `dirs` and `decision`; it never derives them. UI-SPEC §5.3 even bans colouring a tightening in accent, because that would be the panel asserting a judgement.
- **Hardcoding a refusal reason.** There is more than one gate (weekly quota, clock window) and they refuse at different hours. `edit.py:50-58` records this exact bug shipping once already. Surface `decision.reason` verbatim.
- **Optimistic local token math.** `K` comes from `WEEKLY_TOKENS - (effective_spent + M)` using the signer's `effective_spent` (which includes the lazy week reset), never a local decrement.
- **Reading `containsMouse` for colour.** `CursorSurface.qml:4-13` forbids it; hover reports upward and visuals derive from `hasCursor`. This is what guarantees one highlight on screen.
- **A disabled-looking commit button that still fires.** Assert on the *absence of a spawned `pkexec` process*, not on the button's `enabled` property (UI-SPEC control 6).

## Don't Hand-Roll

| Problem | Don't build | Use instead | Why |
|---|---|---|---|
| Format-preserving config edit | A QML/JS YAML writer or line editor | `ngtui.lineedit` via the CLI | A re-emit changes the bytes the signer HMACs; the guard reverts the user's own commit (T-10-09). Indentation-tracked dotted-path resolution already disambiguates `blocking.native_apps.enabled` from `blocking.browser_extension.enabled`. |
| Direction classification | A QML rule table | `nightguard_ctl.classify_change` (imported by `backend.preview_change`) | The signer's `FIELD_TABLE` encodes non-obvious polarities: `allowlist` add **loosens** while `blacklist` add **tightens**; switching *to* allowlist mode **tightens**. |
| Token cost / refusal | Counting lists in QML | `nightguard_ctl.quota_decide` | Lazy week reset, clock window, quota — one function, called by both the preview and the commit. |
| Privileged escalation | An askpass helper, a setuid shim, a PTY | `pkexec` + Omarchy's registered `PolkitAgent.qml` | The agent already exists and is already fingerprint-aware via `/etc/pam.d/polkit-1`. `backend.py`'s 100 lines of `_run_sudo_pty` / `_split_commit_output` / `_AUTH_NOISE` all become deletable. |
| Auth-output parsing | ANSI/PTY scrubbing | Nothing — polkit owns the dialog out-of-process | The caller sees only the CLI's own stdout/stderr and exit code (CONTEXT D-03). |
| Any editing control | A custom toggle/switch/chip/dialog | `qs.Ui` — `Toggle`, `ToggleSwitch`, `ButtonGroup`, `TextField`, `PanelActionButton`, `Button`, `ConfirmDialog`, `CursorSurface` | PANEL-02. Every one reserves its widest border via `BorderSurface` + `Border.controlSpec()`, so hover/cursor/focus change colour only — the no-reflow guarantee comes free. |
| Tooltips | A hand-built popup | Any component's `tooltipText` property | Wired to `PanelToolTip` automatically. |
| Testing the running panel | A screenshot diff, or a human | `IpcHandler` + `qs ipc call` | Already live and verified. |

**Key insight:** every hand-rolled alternative in this table is a *second* implementation of something the signer already decides. The whole reason `backend.py` imports the live trust stack instead of vendoring it (its own module docstring, PORT-02) is that a drifted preview puts an authentication prompt in front of a decision that was already made — which is the failure BLK-04 exists to forbid.

## Common Pitfalls

### Pitfall 1 — the preview and the signer read different clocks, on purpose
**What goes wrong:** someone "fixes" `cache_only_now_minutes` to do a live SNTP query so the preview matches the signer.
**Why it happens:** a cold `.timecache` makes the preview refuse a loosening the signer would allow, which looks like a bug.
**Why it isn't:** `backend.py:150-176` neutralises `guard._sntp`/`_http_time` for the duration of the call specifically because the live path costs ~4s and the preview runs on every stage. Fail-closed is the correct direction. A live query on the stage path re-freezes the UI on every keystroke.
**Warning sign:** a preview that takes seconds, or a `guard._sntp` restore that is not in a `finally`.

### Pitfall 2 — `blocked_urls` parses to `None`, not `[]`, once emptied
Removing the last item leaves `blocked_urls:` with no value; `ngcommon.yaml_load` yields `None`. `classify_change` handles it (`_compare_lists` does `list(new or [])`), but any QML that does `detail.blocking.blocked_urls.length` will throw. Normalise in the payload builder, not in the view.

### Pitfall 3 — the empty-blocklist empty state is `urgent`, and that is correct
UI-SPEC §9.2 renders an empty blocked-apps or blocked-sites list in `root.urgent`, mirroring 12.1's `value_role="error"` (`controlrow.py:330,365`). An empty blocklist means the half of the product that ends applications is doing nothing. Do not "soften" it to `dim` during review.

### Pitfall 4 — a machine fact that was not read must render `—`, never its default
STATE (12.1, plan 07) records that eight of nine facts had no reader and degraded to their documented defaults, and that the `WEAK` alarm was raised *only* when enforcement had actually been read. `home_controls`'s own default is `enforcement = "WEAK"` (`controlrow.py:264`). A panel that says `solo SIGTERM — más débil` because nobody asked is lying in the direction that makes the user trust the tool less. UI-SPEC §7.5 makes this law; the payload must carry a read/not-read distinction, not just a value.

### Pitfall 5 — `Key_Return` double-fires
`PanelKeyCatcher.qml:71-73` emits `returnRequested()` **and** `activateRequested()` for Enter. Wire one.

### Pitfall 6 — a signal-killed `Process` reports exit code 0
`onExited` gives `(exitCode, exitStatus)`. The 10s/120s watchdog `Timer` sets `running = false`, which kills the process; `exitCode` stays 0. `menu/Menu.qml:984-986` records this trap verbatim. A timed-out commit rendered as `✓ aplicado` would be the worst possible lie on this surface.

### Pitfall 7 — the `empower` warning is detection, not prevention
`panel.empower_warning()` exists and works. It tells the user the gate is off *after* it is off. Under `sudo` that was proportionate; under `pkexec` the same group membership makes a token-priced loosening free and silent. Keep the warning **and** add the ordering rule (B-2).

### Pitfall 8 — editing the repo does not change what root runs
`deploy.sh`'s own header says it: *"Run it after every change to the guard sources — editing the repo alone no longer changes what root executes, which is the entire point."* `diff -q scripts/linux/nightguard_ctl.py /usr/local/lib/nightguard/nightguard_ctl.py` currently reports identical; it will not stay that way mid-phase.

### Pitfall 9 — the panel now lists what the old payload deliberately refused to list
`panel.blocking_view()`'s docstring is an explicit privacy decision:

> *"Counts, not names: the panel sits on the desktop where anyone walking past can read it, and the list of what a person blocks themselves from is more personal than the fact that they do."*

BLK-01 requires editing those lists in the panel, which requires showing the names. The popup is click-to-open rather than always-on-screen, so the threat model has changed — but this is a recorded design intent being reversed, and it should be reversed **on the record** (a line in the payload module explaining why, replacing the old rationale) rather than deleted in passing.


### The machine facts have no reader yet (BLK-03)

`panel.blocking_view()` returns `{apps_enabled, mode, games, apps: <count>, sites_enabled, sites: <count>}`. The facts and where they can come from:

| Fact | Source | Notes |
|---|---|---|
| `unmatched_apps` | `appblock.read_processes()` + `appblock.matches_any()` | Needs `/proc` walk; runs unprivileged for the user's own processes. |
| `games` (detected titles) | `appblock.build_catalog(home)` (Steam/Heroic/`.desktop` `Categories=Game`) | Pure filesystem read. |
| `always_allowed` (the floor) | `appblock.is_floor()` / the `_FLOOR` cgroup-slice markers | The structural refusal UI-SPEC §7.3 renders as "no remove button at all". |
| `enforcement` STRONG/WEAK | `appblock.ensure_jail()` / existence of `/sys/fs/cgroup/nightguard` | **Must be read, not defaulted** — `home_controls` defaults it to `WEAK`. |
| `browsers`, `policy_restored` | `verify_browser_lock.py` / the managed-policy files | Read-only. |
| `watchdog` (last tick) | `/var/lib/nightguard/watchdog.log` tail | `root:root 0644`, readable. |

Every one of these is a **read** and none needs root. The payload builder must also carry, per fact, whether it was read at all — a `null`/absent value renders `—` (Pitfall 4), and only a genuinely-read `WEAK` raises the alarm.

## Open Questions

1. **Does the sudoers entry stay after PANEL-03?**
   - Known: `/etc/sudoers.d/nightguard` grants `danitrrga ALL=(root) /usr/bin/python3 /usr/local/lib/nightguard/nightguard_ctl.py commit *, … verify` **with a password**. It is not a bypass — same signer, same gates, same friction.
   - Unclear: whether a second authorised door is acceptable once the sanctioned one is polkit.

2. **BLK-02: per-list charge, or amend the requirement?** See §"The signer charges one token, not one per list" and A6. Belongs in `quota_decide`; does not affect the panel either way.

3. **Where do BLK-03's machine facts run?** All six are unprivileged reads, so they can live in the `ngtui panel` payload. But the `/proc` walk plus a Steam/Heroic catalogue build on every 5s open-panel tick may be too expensive. 4. **Does UI-SPEC's `Style.space(700)` height cap hold with four editable sections plus a staged-changes section?** UI-SPEC §14.2 flags this as considered, not measured. The live walkthrough is its verification; lower the cap if it reaches the screen edge, never remove it.

## Security Domain

### Applicable ASVS categories

| Category | Applies | Standard control here |
|---|---|---|
| V2 Authentication | **yes** | polkit `auth_admin` via PAM (`pam_fprintd sufficient` → `pam_unix required`). Never `auth_admin_keep`, never `yes`. No credential ever enters the panel or the CLI process. |
| V3 Session Management | **yes** | polkit authorisation is per-check and non-retained by construction under `auth_admin` (proven: two back-to-back calls each opened a fresh PAM session). This replaces `sudo -k`. |
| V4 Access Control | **yes** | Admin identity = `unix-group:wheel` (`50-default.rules`). The `empower` group is a documented full bypass (B-2) closed by rule ordering. Sudoers `Cmnd_Alias` remains scoped to fixed subcommands with no bare trailing `*` on the whole command line. |
| V5 Input Validation | **yes** | The signer re-classifies and re-decides everything under root; it never trusts the caller's direction or cost. The CLI recomposes the proposed text from ops rather than accepting a caller-supplied document. `argparse` validates the signer's own argv. |
| V6 Cryptography | **yes (by exclusion)** | HMAC-SHA256 over canonical bytes, key via root-only `.guardkey` (`0600 root:root`). **Nothing in this phase touches it.** `test_port03_no_crypto.py` is the guard and must be extended to the QML. |
| V12 Files & Resources | **yes** | Proposed config travels in a `tempfile.mkstemp()` file (0600, exclusive create), never on a command line. Atomic write + `fsync` + `os.replace` in the signer, under an `flock`. |
| V14 Configuration | **yes** | `.policy` `0644 root:root` in a root-owned dir; rules `0644` in `0750 /etc/polkit-1/rules.d`; code in `0755 root:root /usr/local/lib/nightguard`; data dir `root:root 0755` so the user cannot rename root-owned files aside. |

### Known threat patterns

| Pattern | STRIDE | Mitigation |
|---|---|---|
| `empower` group membership → every polkit action returns YES, no prompt | **Elevation of Privilege** | `00-nightguard.rules` returns `AUTH_ADMIN` first (lexical order + `/etc` precedence). Plus the existing `empower_warning` on the panel. **Control 4.** |
| A `.policy` without `argv1` captures any `pkexec /usr/bin/python3 …` | Elevation of Privilege | `org.freedesktop.policykit.exec.argv1` pinned to the signer's absolute path — `man pkexec` warns about exactly this. **Control 5.** |
| `auth_admin_keep` or `yes` on the action → cached authorisation | Elevation of Privilege / Repudiation | `auth_admin` only. `man pkexec` SECURITY NOTES ties argument-validation risk directly to retained authorisation. **Control 3.** |
| Poisoned `NIGHTGUARD_STACK_DIR` redirects the imported stack **and** the script handed to the escalator | Tampering / EoP | `_resolve_stack_dir()` resolves to an absolute real path and refuses unless it contains `nightguard_ctl.py` (`backend.py:26-48`, CR-02). Must survive unchanged. `pkexec` additionally scrubs the environment. |
| Config content on a command line (visible in `/proc/*/cmdline`) | Information Disclosure | Content always in a 0600 tempfile; argv carries only the path. |
| A refused commit still reaching an auth prompt | — (requirement violation) | `decision.allowed === false` → commit disabled and **no process spawned**. **Control 7.** |
| Poisoned `.timecache` (user-owned) opens the edit window | Tampering | The signer cross-checks true time against the system clock *whatever `clock_protection.enabled` says* (`nightguard_ctl.py:366-391`), and changing the system clock needs a password. Unchanged by this phase — do not "simplify" that check. |
| `config.yaml` ownership flip makes the hand-edit/revert model unreachable | Denial of Service (of a guarantee) | `_chown_back_config` reads `PKEXEC_UID`. **Control 6.** |
| A signal-killed commit rendered as success | Repudiation | `exitStatus` checked alongside `exitCode`. **Control 10.** |
