# Phase 12.2.1: Omarchy Native Panel - Context

**Gathered:** 2026-09-13
**Status:** Ready for planning

<domain>
## Phase Boundary

The dashboard and editor become a first-party-feeling Omarchy shell panel. The plugin at
`packaging/omarchy/plugins/danitrrga.nightguard/` evolves from a read-only viewer into the
full control surface: spend a weekly token, grant grace, and edit the four blocking keys
(BLK-01..05), all committed through the signer. The `ngtui` Textual terminal app is retired
in one deliberate step once the panel reaches parity with it — not incrementally.

This is conformance, not exploration: the panel must read as a first-party panel sitting
beside monitor/audio/network/tailscale. There is no five-family aesthetic search to run.

</domain>

<decisions>
## Implementation Decisions

### Privileged-write gate (settled before this phase was opened, not a discussion item)

- **D-01: `pkexec`/polkit replaces `sudo` on a PTY, and this was proven live on this box,
  not assumed.** Test sequence and evidence:
  - `pkexec whoami` (no PTY) returned root after a real graphical auth dialog. The user
    confirmed seeing and authorizing it (password, since the fingerprint sensor was wedged
    at the time — see the fingerprint-hardware finding below (D-02)). `journalctl` showed a genuine `polkit-agent-helper` session and
    `pam_unix(polkit-1:session): session opened for user root` each call — not a cache hit.
  - Two back-to-back `pkexec` calls each triggered a **fresh** PAM session (new
    `polkit-agent-helper` PID, new D-Bus unique name each time) — confirms `implicit any:
    auth_admin` (from `pkaction --action-id org.freedesktop.policykit.exec -v`) does NOT
    retain/cache, matching the anti-impulse requirement that `sudo -k` currently provides
    (there is no `-k` equivalent needed for `pkexec` — it never caches under this action).
  - Dry-run of the **exact** invocation shape `backend.commit()` uses today — swap `sudo -k`
    for `pkexec`, drop the PTY entirely: `pkexec /usr/bin/python3
    /usr/local/lib/nightguard/nightguard_ctl.py verify` (the `verify` subcommand used as a
    safe stand-in for `commit`) — completed through a real auth dialog with no PTY involved.
  - **No system files were installed** for this proof (no custom polkit `.policy` action) —
    the test used polkit's built-in `org.freedesktop.policykit.exec` action, which is what
    plain `pkexec <program>` invokes. Whether the phase's implementation defines its own
    scoped action (recommended, so the authorization prompt names Nightguard specifically
    rather than "run a program as another user") is a planning-time decision, not a gate
    question — the mechanism itself is proven either way.
  - Omarchy's own polkit agent (`/usr/share/omarchy/shell/plugins/polkit/PolkitAgent.qml`)
    is what answers the prompt — no new agent needs to be written. It reads
    `/etc/pam.d/polkit-1` to detect a fingerprint-configured stack, exactly mirroring
    `backend.commit()`'s own comment about "fingerprint first" — because it is the same
    physical PAM configuration (`pam_fprintd.so sufficient` then `pam_unix.so required`) as
    `/etc/pam.d/sudo`, just reached through polkit's D-Bus flow instead of a TTY.

- **D-02: Fingerprint auth itself did not verify end-to-end on this box during testing — a
  hardware/driver issue, not a gate blocker.** The "Elan MOC Sensors" device raised
  `fpi_ssm_mark_failed: assertion 'machine != NULL' failed` in `fprintd`'s own driver state
  machine and repeatedly denied claims ("Device was already claimed") independent of
  anything nightguard-related — the condition predated this session's first test. Restarting
  `fprintd.service` cleared stuck claims temporarily but the assertion recurred. The user
  confirmed live: *"the fingerprint sensor doesnt work properly"* — touched the sensor,
  nothing registered. This affects `sudo`'s fingerprint path identically (same PAM stack,
  same physical sensor) — it is not a regression introduced by moving to polkit, and is out
  of scope to fix in this phase. Password-based polkit auth is proven; fingerprint should be
  re-verified once the sensor itself is working, but is not a blocker to building the panel.

- **D-03: `nightguard_ctl.py` (the root signer script, pinned at
  `/usr/local/lib/nightguard/nightguard_ctl.py` via `_resolve_stack_dir()`) is "the backend"
  that stays the sole writer/signer.** The panel calls it exactly as the terminal app did —
  same pinned-path resolution, same argv shape (`/usr/bin/python3 <CTL_SCRIPT> commit --from
  <tmp>`), same content-via-tempfile (never on the command line). Only the outer wrapper
  changes: `pkexec` instead of `sudo -k` on a PTY, and none of the PTY/ANSI/auth-chatter
  filtering (`_run_sudo_pty`, `_split_commit_output`, `_AUTH_NOISE`) is needed — polkit's own
  agent owns the dialog entirely out-of-process, so the caller only ever sees the CLI's own
  stdout/stderr and exit code.

### CLI surface the panel calls (new decision, made by explicit request to proceed on judgment)

- **D-04: `ngtui/ngtui/backend.py` and its pinned-path validation SURVIVE the terminal app's
  retirement** — only the Textual layer (`app.py`, screens, widgets — everything importing
  `textual`) is deleted at the retirement step. `backend.py` already holds zero Textual
  imports; it is a pure library over the trust stack (`ngcommon`, `guard`,
  `nightguard_ctl`) that computes preview/classify/quota exactly as the signer will. Keeping
  it means one pinned-path resolution, one classifier/quota code path — not two
  implementations of the same trust-critical logic.
- **D-05: The existing `ngtui` CLI argv router gains two non-interactive subcommands,
  called by the panel via `Process` exactly like the two it already has
  (`ngtui status --json`, `ngtui panel`):**
  - `ngtui preview --from <path>` — unprivileged, wraps `backend.preview_change()`; prints
    the direction labels + quota decision (cost, refusal reason, loosening/tightening) as
    JSON so the panel can show cost/refusal **before** any authentication, per BLK-04.
  - `ngtui commit --from <path>` — thin: builds
    `["pkexec", "/usr/bin/python3", CTL_SCRIPT, "commit", "--from", tmp]` and runs it via
    plain `subprocess.run` (no PTY, no output-scrubbing needed). Exit code + stdout/stderr
    pass straight through.
  This keeps the panel's `Process` calls uniform with what `BarWidget.qml` already does, and
  keeps the pinned-path/validation logic in exactly one place through the transition.

### Editing surface layout

- **D-06: Inline editing within the existing scrollable panel column, not popup-per-field.**
  Matches the first-party idiom in `monitor`/`network` panels and the shell's own component
  set: `ToggleSwitch` for app mode, `Toggle` for game blocking, `TextField` + a removable row
  list for the site blocklist and the allowlist. Edits stage locally in the panel (no signer
  call yet) exactly as the terminal editor staged them. A single `PanelActionButton` commits
  all staged changes; a `ConfirmDialog` gates the actual commit, showing the token cost and
  the direction (loosening/tightening) computed by `ngtui preview` — so cost and any refusal
  are visible before the `pkexec` dialog ever appears, never after.

### Retirement gate for `ngtui` (not a gray area — already locked by the requirements this
phase absorbs)

- **D-07: Full BLK-01..05 parity, including BLK-03's informational surface** (process-match
  highlighting, detected game titles, the allowlist floor, cgroup-vs-SIGTERM enforcement
  strength) **is the retirement bar**, not a "core actions first" cut. These are already
  locked requirements in `REQUIREMENTS.md` under the phase this one supersedes — this phase
  does not water them down.

### Explicit reversal of the Phase 12.1 scope fence

- **D-08:** Phase 12.1's `12.1-CONTEXT.md` scope fence recorded, verbatim from the user at
  the time: *"El panel quickshell... está terminado y me gusta: es la referencia de
  coherencia, y no se toca"* and *"El TUI sigue siendo el único editor y el panel sigue
  siendo ventana, nunca palanca."* This phase is the user's own explicit reversal of both
  constraints — the panel becomes the editor and the lever, and the previously-untouchable
  QML is now exactly what evolves. Downstream agents reading 12.1's context must not treat
  that fence as still active for this phase; it was correct for 12.1's (rejected) scope and
  is superseded here by direct instruction.

### Claude's Discretion
Whether the panel defines its own scoped polkit `.policy` action (named authorization
prompt) versus relying on the built-in `org.freedesktop.policykit.exec` action (generic
"run a program as another user" prompt) is left to planning — both are proven to work;
a scoped action is the more polished default and should be planned unless it adds
meaningful complexity.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `ngtui/ngtui/backend.py` — `preview_change`, `tokens_left`, `edit_window`,
  `edit_window_refusal`, `sanctioned_config`, `commit` (to be re-pointed at `pkexec`) — all
  reusable as-is by new CLI subcommands.
- Shell `Ui/` components listed above — cover every editing control this phase needs; no
  hand-rolled equivalents should be built.

### Established Patterns
- One cursor shared by pointer and keyboard, hover moves the keyboard cursor
  (`UIX-02`, carried from Phase 12.1) — the panel's existing `KeyboardPanel` +
  `PanelKeyCatcher` wiring already follows this; new editable rows must too.
- Read-then-write split: a cheap key-less status poll every 30s
  (`ngtui status --json`) plus a full detail fetch only while the panel is open
  (`ngtui panel`) — the same split applies to `ngtui preview`, called on stage/edit, not on
  every poll tick.

### Integration Points
- `BarWidget.qml`'s `statusProc`/`detailProc` `Process` pattern is the template for the two
  new `Process`es this phase adds (`previewProc`, `commitProc`).
- `NightguardPanel.qml`'s existing `Column` inside `KeyboardPanel` is where the new editable
  rows for the four blocking keys are inserted, alongside the existing token pips and day
  dial.
