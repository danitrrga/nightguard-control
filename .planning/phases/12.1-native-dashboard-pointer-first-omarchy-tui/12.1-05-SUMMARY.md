## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] `.row-detail` had no width, and the row laid out wrong**

- **Found during:** Task 2, while deriving the click offsets from the real cells
- **Issue:** measured on textual 8.2.7, a cell with **no declared width** in a horizontal row
  resolves to `1fr` **against the row's full width** rather than the remainder. The detail
  cell took all 132 columns, the `1fr` value cell was starved to **one**, and its text wrapped
  to **ten lines inside a `height: 1` row**. Every variant measured:

  | `.row-detail` | label | value | detail |
  |---|---|---|---|
  | (nothing declared) | 18×1 | **1×10** | **132×1** |
  | `content-align: right middle;` only | 18×1 | **1×10** | **132×1** |
  | `width: 1fr` | 18×1 | 57×1 | 57×1 |
  | `width: auto` | 18×1 | 103×1 | 11×1 |

- **Why no control in this phase would have caught it:** the row's `content_size` stayed
  `(132, 1)` throughout, so control 7 is blind to it by construction — it asserts the row's
  box, and the bug is inside it.
- **Fix:** `.row-detail { width: auto; … }`, with the measurement in the CSS comment. All
  eleven rows now sum to 132.
- **Files modified:** `ngtui/ngtui/app.tcss`
- **Commit:** `30f75ac`

**2. [Rule 1 — Bug] `Message.control` cannot be assigned**

- **Found during:** Task 2, on the first activation
- **Issue:** `Message.control` is Textual's own property for "the widget this message is
  about". Carrying the row model under that name raised
  `AttributeError: property 'control' of 'ControlRow.Activated' object has no setter`.
- **Fix:** the model rides as `.model`; `control` is overridden as a property returning the
  row, so `message.control` means what a Textual reader expects.
- **Files modified:** `ngtui/ngtui/widgets/controlrow.py`
- **Commit:** `30f75ac`

**3. [Rule 2 — Missing critical functionality] `j` moved nothing**

- **Found during:** Task 2
- **Issue:** the plan's own success criterion is "hover a row, press `j`, land on the next
  row", and nothing in the product bound `j`. Only a test-local screen binding would have made
  control 5 pass — which would have asserted the test harness rather than the product.
- **Fix:** `j`/`k`/`down`/`up` on `ControlRow.BINDINGS`, `show=False`, filtered to
  `ControlRow` so the walk visits the registered order. On the widget rather than a screen
  because the cursor belongs to the control strip, not to whichever composition hosts it.
- **Files modified:** `ngtui/ngtui/widgets/controlrow.py`
- **Commit:** `30f75ac`

**4. [Rule 2 — Missing critical functionality] the paint ladder was guarded by nothing**

- **Found during:** requirement review after Task 3
- **Issue:** UIX-02's text names two things — the shared cursor **and**
  `pressed > focus > hover/cursor > selected > idle`. The ladder is implemented (plan 04) and
  its mechanism is **rule order**: `:focus` counts as a class, so `.ctl:focus` and
  `.ctl.-pressed` tie on specificity and the later rule wins. Plan 04's handover warns that
  re-sorting silently changes what a focused-and-pressed row paints. No control in
  `VALIDATION.md` covers it, so a tidy-up that sorted six lines would have been invisible.
- **Fix:** `test_the_paint_ladder_keeps_its_priority` — four rungs proved **distinct** first
  (one rung alone cannot tell a wired ladder from a flat one), then pressed > cursor, cursor >
  selected, pressed > selected. Against the fixture theme, whose rungs are pinned to
  0.42 / 0.08 / 0.18 / 0.22.
- **Files modified:** `ngtui/tests/test_dashboard_cursor.py`
- **Commit:** `448ff17`

**5. [Rule 2 — Missing critical functionality] the alarm role painted nothing**

- **Found during:** Task 1
- **Issue:** `ControlRow` carries colour as a role *name* (the mechanism that makes the hex ban
  scannable). `app.tcss` had `.row-value` and `.row-detail` but no role variants, so
  `no site is blocked` and `discord matches nothing` would have carried the `error` role and
  rendered in the ordinary ink — a silent alarm, which is worse than no alarm.
- **Fix:** `.row-value.error|warning|success` and `.row-detail.error|warning`. The refused
  rule `.ctl.-refused .row-value` is three classes and still wins the tie, so a refused row's
  value drops to the quiet channel whatever role it carries.
- **Files modified:** `ngtui/ngtui/app.tcss`
- **Commit:** `cf2c39e`

## Decisions Made

- **A refused row posts `Refused`, not `Activated`.** The plan says a refused row "must not
  push the edit screen". Making that a *type* rather than a convention means a screen handler
  written as `on_control_row_activated` → open the editor is structurally unreachable from one
  of the four frozen keys. 12.2 flips one field in the registry and the row starts posting the
  other message; the widget, the ladder and the budget are untouched.
- **The both-at-once invariant is asserted at both layers, separately.** The constructor guard
  and the registry walk are two tests, not one, so a red names which layer rotted. This is the
  shape prior waves kept being bitten by, applied on purpose rather than in hindsight.
- **`j`/`k` live on the widget.** A screen-local binding has to be re-declared on every surface
  that grows a control, and eventually one of them gets it wrong. `focus_next(ControlRow)`
  also keeps the walk on controls rather than on every focusable widget that happens to be
  mounted.
- **Click offsets are derived, never typed.** The 6b test reads where the three cells actually
  landed and clicks the middle of each plus the spine column and the last addressable column,
  asserting first that no cell is zero-wide. A hardcoded `x` that drifts off the cell it was
  meant to cover turns a three-cell control into a one-cell control with no output. The probe
  rows carry a non-empty detail for the same reason: the detail cell is `width: auto`, so an
  empty one is **zero** columns and the "far right edge" click would land back on the value.
- **Control 7 has a vacuity guard on the reservation itself.** An idle row must already paint
  `vkey`. If idle ever became `border: none`, all four measurements would agree at the *wrong*
  value and the control would pass on a row that reflows the moment it is hovered.
- **`switch_display` uses reverse video, not colour.** Two cells, filled versus hollow, plus
  the word. Reverse video is a terminal *attribute*, so the distinction survives a monochrome
  terminal and a colour-blind reader both — which is what UI-SPEC §11 asks and what a coloured
  dot would not give.

## Issues Encountered

**`styles.background` is the animated value.** Reading it straight after a class change
returned **0.2037** for a rung whose settled alpha is **0.08** — an intermediate frame of the
120 ms fade from 0.18. `pilot.pause()` waits for the message queue, not for the animator. Any
later control that samples a transitioning property must settle past the transition; the
ladder test derives its settle from `PRESS_FLASH` rather than typing a number, so a change to
the transition cannot leave it sampling the middle of the fade.

**The cursor tests run against the *live* desktop theme.** Controls 5, 6, 6b, 7 and 8 assert
geometry and timings only, so they are theme-independent and do not need the fixture — but
they do construct a real `NightguardApp`, which means a `hyprctl` per app (~7 ms) and a read
of whatever theme is installed. The ladder test requests `omarchy_theme_dir` because it is the
only one of the six that asserts a *value*. If a later control asserts colour, it must take
the fixture too (T-12.1-02).

**Five stops are not `route`-able and never will be from here.** `ramp` and `enforcement` by
nature; the four frozen keys until 12.2. That is 6 of 16 stops whose activation currently does
nothing visible beyond surfacing a refusal — expected at this wave, and the reason the
`Refused` message exists rather than a silent no-op.
