# Phase 12.1 — what was proved before planning

Two things this phase rests on were probed against the installed `textual 8.2.7`
headlessly, so the plan does not have to assume them. Probes live in the session
scratchpad; the results are what matter and are recorded here.

## 1. The shared cursor is real, and it is testable

The pattern taken from Omarchy's kit — a control is hot when the pointer is over it *or*
the keyboard cursor is on it, and **mouse-enter moves the keyboard cursor** so the two can
never disagree (`Ui/Button.qml`'s `hot = containsMouse || hasCursor` plus the
`hovered(bool)` signal that `plugins/panels/monitor/Panel.qml` binds to its own cursor
model).

In Textual the pieces are: a focusable widget with `on_enter` calling `self.focus()`, plus
`:hover` and `:focus` in CSS. Probed with `App.run_test()` and `Pilot`:

```
initial focus: r0
after hover #r2, focus = r2 | :hover matched = True
after 'j',      focus = r3   <- continues from where the pointer left it, not from r0
```

That third line is the whole contract, and it is **assertable in a test** — `pilot.hover()`,
then `pilot.press("j")`, then assert `app.focused.id`. So the shared cursor is verifiable rather than merely
claimed (UIX-02).

Also confirmed on real widgets in the same run:

| Needed | Result |
|---|---|
| `:hover` pseudo-class | matches |
| pointer moves keyboard focus | yes, via `on_enter` → `self.focus()` |
| right-click / double-click | `Click.button` (1 = left, 3 = right) and `Click.chain` (2 on double) both populated |
| colour transition | `styles.transitions` populated from `transition: background 120ms` |
| tooltip | `Widget.tooltip` works |

**One concrete adjustment**: `App.TOOLTIP_DELAY` defaults to **0.5 s**, and Omarchy's kit
uses **0.4 s** (`ToolTip { delay: 400 }` in `Ui/Button.qml`). Matching the desktop means
setting `TOOLTIP_DELAY = 0.4` on the app — a one-liner that would otherwise be missed,
because the default is close enough to look deliberate.

## 2. The 135 × 46 overflow control can be proved able to fail

The overflow control (UIX-06) asks for a test that fails when the layout outgrows the
sanctioned window. The
mechanism is `App.run_test(size=(135, 46))` and comparing the container's `virtual_size`
against `screen.size`:

```
 40 rows of content -> content_height=46  overflows=False  max_widget_bottom=40
 46 rows of content -> content_height=46  overflows=False  max_widget_bottom=46
 60 rows of content -> content_height=60  overflows=True   max_widget_bottom=60
```

The assertion **discriminates** — it passes at 40 and 46 and fails at 60 — which is the
negative control, and it is recorded here so the plan does not have to re-derive it.

**Careful**: `show_vertical_scrollbar` was `False` even while overflowing, because a
container only grows one when its overflow is `auto`/`scroll`. So a scrollbar is *not* a
reliable overflow signal. Use `virtual_size.height > screen.size.height`, or
`max(w.region.bottom for w in app.query(...))`, which was the clearer of the two.

## 3. Pre-existing red on the active theme, and why it is not fixed here

Baseline before any work, `uv run --with pytest --with pytest-asyncio pytest -q` in
`ngtui/`: **458 passed, 1 failed, 3 skipped**.

```
AssertionError: dos-moos.surface is #343f44, which the theme does not declare — it fell back
tests/test_theme_sync.py:93
```

`panel.py:232` picks the `surface` role from `lighter_background` or `selection`. Of the 28
installed themes, **dos-moos is the only one that declares neither** — so it is the only one
whose panel surface falls back to everforest's grey, and it is the theme actually running.
In an ANSI palette the "lighter background" role is `color8`, which dos-moos does declare
(`#3A4849`).

The fix is one name added to that pick chain. It is **not applied**, because it changes the
appearance of the bar panel the user explicitly placed out of bounds — it is his call. It is
recorded here because the same role-mapping gap will bite the token pipeline (UIX-01) the moment
surfaces are wired from the theme, and because a phase whose success criterion is "the suite stays green"
needs its baseline red named up front rather than discovered later.

## 4. The day ramp can be read by hover, per column

The hero (UIX-04) claims that hovering any column of the ramp reads out that hour. That
needs the widget to know which cell the pointer is over. `MouseMove.offset.x` gives the
column *inside* the widget, and `tooltip` can be reassigned live:

```
column -> hour readout: [(0, '00:06'), (29, '05:54'), (59, '11:54'), (107, '21:30')]
tooltip now: 21:30      widget width: 120
```

Column 107 of 120 resolves to 21:30 — the curfew start — so the mapping lands where it
should rather than approximately. The readout is therefore real behaviour, not a caption,
and it is assertable with `pilot.hover("#ramp", offset=(col, 0))`.

That closes the last unproven interaction claim in the phase: the shared cursor, the
overflow control and the per-column readout are all demonstrated against the installed
package, so the plan can treat them as mechanics rather than as bets.
