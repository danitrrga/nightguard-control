### The window budget — three claims, and each catches what the other two call fine

The plan prescribed `virtual_size.height <= 46` and `max(region.bottom) <= 46`. **The
first of those as written is blind**, and that is measured: `frame.virtual_size.height`
is the frame's **inner** height (44 at the sanctioned size, because the two border rows
are outside it), so comparing it against the window's 46 hands the assertion two free
rows on top of the ledger's three. It was corrected to compare against
`frame.container_size.height` — at which point it became the *same* claim as
`max_scroll_y`, which is stated in the docstring rather than dressed up as independence.
`overflow-y: hidden` on `#frame` did **not** separate them (`max_scroll_y` stayed 1 with
the overrun present).

What replaced it is the claim it was reaching for — the frame fits the window. The three
that ship:

| Claim | Arm | Message |
|---|---|---|
| content fits container (`max_scroll_y == 0`) | +4 rows of content in `compose()` | `at the sanctioned window: the composition outgrew the 46-row window by 1 rows — it is scrolling instead of fitting` · `assert 1 == 0` |
| the frame fits the window | `#frame { height: 50 }` | `the frame is not the window — Region(x=0, y=0, width=133, height=50) against 46 rows` |
| no widget's bottom past the last row | `#chips { offset: 0 6 }` | `11 widget(s) reach past row 46 — the lowest is at 50: [('chips', 50), ('ctl-chip-edit', 50), …]` |

The second and third arms both leave `max_scroll_y == 0`; the third leaves the frame's
region exactly right and `virtual == container == 44` as well. Three arms, three claims,
no two catching the same bug.

### Where the fit claim starts firing — the finding this plan inherited, re-measured

Plan 07 measured that one extra row is invisible to `max_scroll_y` and that ten were
needed. With `#ledger { min-height: 4 }` the ledger can only absorb its 3 rows of slack,
so the threshold moves to **four**:

```

+3 rows (49 total) -> GREEN, blind
+4 rows (50 total) -> RED: outgrew the 46-row budget by 1 rows
+14 rows (60 total, RESEARCH's figure) -> RED: outgrew ... by 11 rows
```

**The 1-to-3-row blind spot is real and is named in the docstring.** What catches it is
`test_dashboard_home.py`'s third claim, armed with one extra row:

```

   next phase needs 3 of them

```

The two controls are halves of one guardrail. Neither is sufficient, and this is written
where the next person will read it rather than only here.

**1. [Rule 2 — Missing critical functionality] the audit ledger had no floor**

- **Found during:** Task 1, probing the degradation handler at 30 rows
- **Issue:** UI-SPEC §7.2 and T-12.1-32 both state "the ledger never goes below 4", and
  nothing enforced it. Measured: the `-compact` + `-tiny` composition's fixed rows total
  27, so the ladder reaches the floor at exactly 31 rows and has nothing left to drop

  control 9's fit claim now fires at +4 rows instead of plan 07's measured +10.

## Known Stubs

**The editor has no on-screen legend any more.** `EditScreen`'s seven bindings — `j` `k`
`enter` `space` `c` (commit) `u` (discard) `escape` (back) — lost their only affordance
when the `Footer` went, and the home surface's replacement (the `help` chip) does not
exist on the editor. Measured: `textual 8.2.7` binds nothing to `f1`; `App.BINDINGS` is
`ctrl+q` and `ctrl+c`, `Screen.BINDINGS` is `tab`, `shift+tab` and `ctrl+c,super+c`. So
there is no free fallback.

Not closed here because the plan fences `edit.py` to three `yield` lines and one import
(T-12.1-31) and because the obvious fix collides with the editor's own semantics:
`escape` is already this screen's cancel, so a help panel that `escape` both closes and
escapes out of is a rework of the edit flow. Logged in `deferred-items.md` with the shape
that would close it. **This is saying so, not routing around it.**

**`backend.py` was not touched**, so plan 07's eight unread machine facts are unchanged
and still degrade to their documented defaults. Nothing in this plan reads or needs them.

## Issues Encountered

**The plan's prescribed assertions were blind in three of the ways this phase has been
finding all along, and arming is what found every one of them.** Claim 2 compared an
inner height against an outer one. The widget-bottom scan measured a third-party widget.
The `cell_len` choice was invisible on today's composition. None of the three is visible
by reading the assertion; all three are one arm away. That is prior-wave finding 12 for
the eighth consecutive wave, and the ratio held: **eleven arms, nine fired, two did not**
— and both that did not are documented above with the assertion that does catch them.

**`on_resize` keys on the SCREEN's size, and a `split` panel does not resize the screen.**
Measured frame width with the help panel open:

```
terminal 135 -> frame 91 cols   (above the 80-col -narrow threshold: fine)
terminal 120 -> frame 81
terminal 110 -> frame 74
terminal 100 -> frame 67
terminal  90 -> frame 60
terminal  80 -> frame 50        -- and #frame wears no class at any of these
```

At the sanctioned 135 the panel leaves 91 columns, well above the threshold, so **the
shipped window is unaffected**. Below about 120 the band stays side-by-side while its
fixed 62-column left half no longer leaves room for the right one, and `overflow-x:
hidden` clips `THIS WEEK` rather than stacking it. Vertically the frame still fits at
every width measured, so nothing scrolls and no ledger row is hidden — it is a
narrow-terminal cosmetic loss while a transient panel is open. Fixing it means moving the
trigger from the screen's size to the frame's own, which changes what UI-SPEC §7.4's
"< 80 columns" is measured against and so needs the contract updated with the code.
Logged in `deferred-items.md`; the first arm attempted for the help-panel control is what
exposed it.

**The 16 stops are 15 rows plus the hero.** `screen.query(ControlRow)` returns 15; the
`DayRamp` is a `CursorStop` and not a `ControlRow`. The plan's `max(w.region.bottom for w
in app.query(ControlRow))` would therefore have measured the rows and silently excluded
the screen's one idea. The control queries `CursorStop` and asserts 16, armed by removing
the hero from `compose()`.
