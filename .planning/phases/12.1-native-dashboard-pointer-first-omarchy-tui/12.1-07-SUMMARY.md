## Scope item A — the flake, and two corrections to its diagnosis

`tests/test_token_pipeline.py::test_controls_fill_alpha_reaches_the_row` measured
**17/20** entering this plan. It measures **30/30** now. Both corrections below are
measured, not reasoned, and both matter to anyone who hits this again.

### It was the cursor read, not the idle one

`deferred-items.md` attributed the flake to `idle = rows[1].styles.background`. Every
captured failure was on the **cursor** read, `rows[0]`:

```
E  AssertionError: the focused row is not on the cursor rung:
   Color(169, 192, 191, a=0.2206199511291925)
E  assert 0.2206 == 0.08
   ... a=0.26817870630649854 and a=0.12513740546205854 on two other runs
```

0.42 → 0.08 is exactly the `.ctl` fill cross-fade and 0.22 / 0.27 / 0.13 are frames of
it. `rows[1]` is idle and is **never animated**, which is why it never flaked. The
cause plan 05 recorded was right; the assertion it lands on is the one that changes
rung on mount, not the one that stays put.

### Textual's own wait helpers do not work here

The obvious fix — `await pilot.wait_for_scheduled_animations()` — measured **23/30**.
Traced:

```
TRACE [('_animate', 'background'), ('start', 1)]
```

`Animator.start()` sets `_idle_event` **and** `_complete_event` unconditionally
(`_animator.py:259-260`) and runs **after** the first `_animate` — `start` sees one
animation already in `self._animations`. So for the first animation of an app's life
both events are set while the fade is in flight, and both `pilot.wait_for_animation()`
and `pilot.wait_for_scheduled_animations()` return immediately. Sampled with an
animation live:

```
pause        bg=0.2674 anims=1 sched=0 idle=True complete=True being=True
wait_anim    bg=0.2674 anims=1 sched=0 idle=True complete=True being=True
wait_sched   bg=0.1255 anims=1 sched=0 idle=True complete=True being=True
```

`_settled_background()` establishes settlement two independent ways: a wait **derived
from `styles.transitions["background"]`** (so retuning the transition in `app.tcss`
retunes the wait with it), then `animator.is_being_animated` keyed on `styles.base` —
the object `Stylesheet.replace_rules` hands to `animator.animate`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] The chip strip painted as five empty brackets**

- **Found during:** Task 2, on the first mount of the composed strip
- **Issue:** `ControlRow` declares `layout: horizontal`, which makes it a **container**,
  and a container's `width: auto` is computed from its children. A chip carried its
  label as the widget's own renderable and its `compose()` yielded nothing, so it
  resolved to width 0 and the strip painted `▏  ▕ ▏  ▕ ▏  ▕ ▏  ▕ ▏  ▕`.
- **Why nothing caught it earlier:** the chip path in `controlrow.py` was dead until
  this plan. Plan 05's controls construct chips but never lay one out.
- **Fix:** a chip composes one `.chip-label` cell, the same way a row composes three.
  `.chip` also gains `width: auto`, for plan 05's own measured reason.
- **Files:** `ngtui/ngtui/widgets/controlrow.py`, `ngtui/ngtui/app.tcss`
- **Commit:** `72bedb5`

**2. [Rule 1 — Bug] `l` collided with the `ledger` binding and the ledger was unreachable**

- **Found during:** Task 2, by the chrome control — `fired` came back
  `['edit', 'refresh', 'quit']`
- **Issue:** `DayRamp` bound `h`/`l` for the read-out, and the ramp holds the cursor on
  mount because it is stop 1 of 16. `l` therefore reached the ramp and the ledger
  toggle was unreachable **from the screen's opening state**.
- **Fix:** the ramp yields. `e r l q` are pinned to `NightguardApp` by
  `tests/test_port01_single_key_bindings.py` and are a locked contract; the ramp's
  `h`/`l` are plan 06's newer choice and are not in UI-SPEC. Both go — `h` alone
  teaches a vim habit that works one way and silently does something else the other.
  `left`/`right` were already bound to the same two actions. Control 11c presses them
  now and its claim is unchanged.
- **Files:** `ngtui/ngtui/widgets/hero.py`, `ngtui/tests/test_dashboard_hero.py`
- **Commit:** `72bedb5`

**3. [Rule 2 — Missing critical functionality] the help panel was a one-way door**

- **Found during:** the requirement review after Task 2
- **Issue:** UIX-03's text names `Escape` among the keys that drive everything.

## Known Stubs

**Eight of `home_controls()`'s nine machine facts have no reader, and this is deliberate.**

`_machine_facts()` supplies exactly one key, and it is not a machine fact at all:
`blocked_sites` is `blocking.browser_extension.blocked_urls`, a **signed config key**
(`nightguard_ctl.py` FIELD_TABLE), read from the config the paint already holds.

The other eight — `enforcement`, `watchdog`, `games`, `game_blocking`, `browsers`,
`policy_restored`, `always_allowed`, `unmatched_apps` — have **no reader anywhere in
`ngtui`**, and this plan's stop condition says outright:

> If a row, a chip or the ledger appears to require touching `ngtui/ngtui/backend.py`
> … **stop and say so.** Do not route around it.

So they are left unsupplied and `home_controls` degrades each to its own documented
honest default. **This is saying so.** The consequences visible on screen:

| Row | What it shows today | Why |
|---|---|---|
| `enforcement` | `WEAK` · `SIGTERM fallback · watchdog never` | the fact is unread; `WEAK` is the pessimistic default and the only direction this product may fail in |
| `game blocking` | `off` · `0 titles installed, covered by nothing` | no game detection is read |
| `always allowed` | `the floor only` · `0 entries ▸` | no floor list is read |
| `site blocking` | detail empty | no browser count, no policy-restored time |
| INTEGRITY right | `watchdog never` | same degradation as the `enforcement` row's detail, rendered identically on purpose |

**The one place the default is NOT allowed to speak** is the header's `WEAK MODE`
alarm tag. `_weak_mode()` raises it only when `enforcement` was actually **supplied**,
never by the unread default: "enforcement is weak" and "enforcement was not read" are
different claims, and an alarm that is always on is an alarm nobody reads on the night
it is true.

A future plan that adds these reads to `backend.py` fills `_machine_facts()` and
nothing else changes — the rows, the tag and the INTEGRITY line all move together
because they all read one dict.

**A routed row opens the editor, but not *on* its field.** `EditScreen.__init__` takes
no argument, and giving it one is new editing capability in a file this plan does not
own. The route rides on the stop unused; that is the 12.2 seam, and it is deliberately
not routed around.

## Decisions Made

- **The cursor walk is a property of being a stop, not of being a row.** `CursorStop`
  owns the two bindings and the two actions; `ControlRow` and `DayRamp` inherit them.
  A second `focus_next` on `DayRamp` would be two code paths that agree until one is
  edited — the shape control 11c exists to catch.
- **A base class rather than a marker CSS class.** `Screen._move_focus` resolves a type
  to `selector.__name__` and matches it against `_css_type_names`, which
  `DOMNode.__init_subclass__` fills from the DOMNode ancestor chain. The shared base is
  matched by the same machinery that matched `ControlRow`, and there is no class to
  remember at each construction site.
- **`cursorstop.py` is its own module.** `controlrow.py` reads `EDITABLE_FIELDS` from
  `widgets/edit.py`, which imports `backend` at module level; `hero.py`'s pure helpers
  must stay importable with no LifeOS stack on `sys.path`, and plan 06 measured that.
- **Every value is read once, in `_read()`, and handed down.** A region that reached
  back into `backend` for its own copy is how a token count and a verdict rendered in
  the same frame come to describe different moments (T-12.1-24).
- **`theme_name()` is called at paint, never cached.** `omarchy-theme-set` writes
  `theme.name` ~440 ms after renaming the theme directory, so a watcher that fires on
  the theme files can read the previous name and then keep showing it forever, having
  already consumed the event. Observed live: `acepe · Europe/Amsterdam · 12:44`.
- **The timezone comes off the signed config**, not `backend._tzname` (a private) and
  not the system's. The guard evaluates the curfew in the signed zone; a header
  printing another one describes a different day.
- **`_remaining_seconds()` is one source for the countdown and the meta line.** They
  are two renderings of one number, and computing it twice is how they drift by a
  second and read as a glitch. `_hhmmss` always emits three fields so the one
  tick-refreshed cell cannot change width mid-tick (UIX-05).
- **Spacing is blank ROWS, not margins.** `.kv-row` and `.advisory` lost their
  `margin: 1 1 0 1`. A margin does not appear in a row count, which is exactly how a
  46-row budget stops being checkable.
- **The band's two control rows get their detail filled at compose**, with
  `dataclasses.replace`. The registry is pure and has no verdict, clock or remaining
  time; `CURFEW · 7H 38M REMAINING` and `open now` / `shut now` are exactly that. Key,
  order, route and refusal are untouched, so the 12.2 seam is unaffected.
- **The read-only notice is counted from the registry**, not typed. A typed
  "4 of these" goes stale the moment 12.2 turns one refusal into a route, and silently.
- **`_section()` asserts its label is one of the six.** Tracking costs `2n − 1` cells
  and is permitted for those labels only; putting the assertion at the one call site
  means nothing else can be tracked by accident.
- **The ledger-empty copy is UI-SPEC §10.6's, not the helper's.** `ledger_rows()` is a
  carried-forward pure helper whose exact output `tests/test_status.py` pins, so it is
  used as the **emptiness signal** and the contract's two lines are what the surface
  shows.

## Issues Encountered

**A probe composition and the shipped composition are different subjects, and this
phase has now been bitten by that twice in two plans.** Control 6 walks sixteen of
sixteen on a probe where every stop is a `ControlRow`; the shipped screen walks
fifteen. The chip path in `controlrow.py` had been constructed by tests and never laid
out, so it was width 0. Both were invisible until something composed them. Every
control in `test_dashboard_home.py` mounts the real `StatusScreen` for that reason.

**`max_scroll_y == 0` is not a budget check on its own** — see the control record. The
flexible region absorbs the overrun and the surface reports that it fits. Plan 08 owns
the overflow controls; it should assume the same blindness applies to its own.

**The vertical `Rule` inherits `height: 1fr` from `Rule.-vertical`'s DEFAULT_CSS**,
which is why the band's keyline spans all six rows without a rule of its own. App CSS
beats DEFAULT_CSS regardless of specificity, so plan 04's `Rule { margin: 0 }` still
kills the horizontal margin.

**`Static` with `width: auto` in a horizontal row is 0 when the widget declares a
layout.** This is the third distinct form of plan 05's width finding to bite in this
phase. Declare a width on every cell, and give a container a child.
