<objective>
Make the day an instrument rather than a number.

A full-width ASCII density ramp where density is hours-until-curfew, a second channel
underneath marking the hours a loosening is accepted, and one bright cell for now. Hovering
any column reads out that hour and whether a loosening would be accepted there — proved
workable before planning: column 107 of 120 resolves to 21:30, the exact curfew start, so
the mapping lands where it should rather than approximately.

Purpose: the hero is the screen's one idea and the strongest case for the
meaning-never-rides-on-colour-alone rule rather than an exception to it. It is greyscale on
purpose: density carries the whole meaning, so it survives a monochrome terminal intact, and
the colour budget belongs to the verdict.
Output: `hero.py`, and the three hero controls.
</objective>

  <action>
    Create `ngtui/ngtui/widgets/hero.py` with the same literal two-section structure
    `status.py` uses: every pure function above the divider, importable with no App, and the
    widget below it doing nothing but painting.

    **`density_index(minute, curfew_start_minute) -> int`.** Character set `" .:-=+*#%@"`,
    index 0-9. Inside the curfew → 9; under 1 h → 8; under 2 h → 7; under 3 h → 6; under
    4 h → 5; under 6 h → 4; under 8 h → 3; under 11 h → 2; otherwise 1.

    **Index 0 — the space — is never emitted.** A blank cell in the day reads as *missing
    data*, not as "far from the curfew". That is the whole reason the range starts at 1 and
    the reason control 11 exists.

    **`column_minute(i, width) -> int`** = `int(((i + 0.5) / width) * 1440)`.
    **`width` is an argument and never a constant.** The contract's own rule is "no literal
    ramp width in code", and the measurement behind it: at width 120 column 107 reads 21:30,
    but at the real content width of 129 that same column reads 20:00 and the first column
    inside a 21:30 curfew is 116. A constant is what silently breaks when the frame or the
    gutter changes.

    **`permission_channel(width, window) -> str`** — `▔` where the minute falls inside the
    edit window, space elsewhere. Read from the **signed** config's `edit_window` and its
    timezone, never from the system clock's. One row, one glyph, no colour: it is a second
    channel, not a second hero.

    **`hour_axis(width) -> str`** — two-digit hour labels every 2 hours, in the quiet channel.

    **`readout(column, width, cfg) -> str`** — the exact copy:
    `09:14   open · a loosening is allowed here` and
    `21:52   curfew — locked · a loosening is refused here`.
    The window bounds it reports come from the signed config and its timezone. The TUI never
    invents a reason it did not read.

    Every helper takes plain arguments and returns a string or an int. No App, no `backend`
    import inside the helpers themselves — the widget passes the values in, which is what
    makes all 1440 minutes testable headlessly.

    Docstrings per the house convention: what it is, then why, naming the day-as-instrument
    decision (D-06) and the requirement (UIX-04), and stating the meaning-without-colour
    property explicitly — this ramp is greyscale by design, so density carries everything.

  <action>
    **`DayRamp`**, below the divider, focusable so it is stop 1 in the cursor order.

    **Colour: greyscale, computed from the resolved foreground.** Each run is the foreground
    at `0.30 + 0.055 × d` alpha; hours inside the curfew at `0.92`. Read
    `app.theme_variables["foreground"]` — the **resolved** runtime value, not the theme
    file's text, because Textual's colour system shifts some roles. That read is a resolved
    runtime value rather than a literal, so it does not trip the hex scan, and it is the one
    place a widget legitimately touches a colour at all.

    **The alpha must not reach `rich`.** Measured:
    `Color.parse("#a9c0bf").with_alpha(0.355).hex` produces the 8-digit `'#A9C0BF5A'`, and
    `rich.style.Style.parse` raises
    `StyleSyntaxError: unable to parse '#a9c0bf5a' as color` — so a `rich.text.Text` route
    dies at first paint. Use Textual's own `Content` with
    `textual.style.Style(foreground=fg.with_alpha(a))`, which blends against the widget's
    real background and survives a region that paints its own. The fallback, if `Content` is
    ever unavailable, is to blend explicitly and pass six digits via `bg.blend(fg, a).hex`.
    Both routes were measured to produce identical cells; prefer `Content`.

    **The now marker: exactly one cell**, `█`, bold, at `floor(now_min / 1440 × width)`, in
    the foreground at full strength. One bright cell, one marker.

    **Width is measured at paint time**, from the widget's own content size — the ramp, the
    keylines and the chip strip are all `1fr` and must be generated from the measured width.
    The sketches drew them at a constant 127; a constant is what silently breaks when the
    frame or gutter changes.

    **The read-out has two inputs and one destination**, which is the reserved row beneath
    the axis — reserved precisely so nothing reflows when it fills:
      - Pointer: `on_mouse_move` → the column from the widget-relative `x` → the read-out.
      - Keyboard: with the cursor on the ramp, `h` / `l` move a column index and write the
        **same** string. Keyboard parity is mandatory, which is why the read-out cannot be
        tooltip-only: a tooltip is unreachable without a pointer.

    The ramp's **tooltip** carries the explanation of what the instrument is — density is
    hours until the curfew, the underline marks the hours a loosening is accepted, the bright
    cell is now — not the per-column value.

    The ramp is **never dropped** under any degradation class. It is the screen's one idea.

    Activating the ramp does nothing: it is a read instrument, and it is stop 1 in the cursor
    order for the `h`/`l` read-out, not for an action.
  </action>
