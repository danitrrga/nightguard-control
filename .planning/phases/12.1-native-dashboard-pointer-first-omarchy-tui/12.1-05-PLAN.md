<objective>
Build the one widget the whole interaction contract rests on: a control row whose highlight
is shared between pointer and keyboard because there is only one of it.

Omarchy's own kit does this with `hot = containsMouse || hasCursor` plus a `hovered(bool)`
signal that the panel binds to its keyboard cursor. In Textual the cursor **is** focus, so
`on_enter` calling `self.focus()` gives the same guarantee with one model rather than two —
and two models are how a pointer and a keyboard end up disagreeing. The codebase already
contains the anti-pattern this replaces: `EditScreen._highlight_focus` maintains a
`self._focus` index beside Textual focus. Do not port it.

Purpose: "it looks like the old one" was about behaviour, not pixels. This is the plan that
changes the behaviour.
Output: `ControlRow`, the 16-stop registry, and the five interaction controls.
</objective>

  <action>
    Create `ngtui/ngtui/widgets/controlrow.py` following the house architecture stated in
    `status.py`'s docstring: pure helpers above a divider, Textual widgets below it that only
    compose them.

    **The row model.** One immutable shape per stop: `(label, value, detail, route | refusal)`.
    A `route` is a dotted config key handed to the existing edit surface; a `refusal` is a
    string. A row has exactly one of the two, never both — that invariant is what makes phase
    12.2's whole job on this surface a one-field swap, with no change to the row widget, the
    ladder or the budget.

    **The registry.** A pure function returning the ordered control list for the home
    surface, built from values read through `backend`'s existing public reads. Eleven rows
    plus five chips, in the order the contract fixes:
    the day ramp; `curfew`; `may weaken`; `app blocking`; `mode`; `blocked apps`;
    `always allowed`; `game blocking`; `site blocking`; `blocked sites`; `enforcement`;
    then the chips `edit` `ledger` `refresh` `help` `quit`.

    Four rows carry a **refusal**, not a route — `mode`, `always allowed`, `game blocking`
    and `blocked sites`. Their refusal string is the contract's verbatim copy:
    `unreachable — the only sanctioned editor cannot change this yet`. That is presentation.
    **It is not enforcement** — the signer still refuses, through the direction classifier and
    the edit window, and this plan adds no UI-side allow/deny decision.
    `enforcement` is machine state rather than config: it has neither a route nor a refusal
    and activating it does nothing.
    The day ramp is a read instrument: activating it does nothing; `h`/`l` move its column
    read-out, which is the next plan's widget.

    Routes use dotted keys that already exist in `EDITABLE_FIELDS` — `curfew.start`,
    `edit_window.start`, `blocking.native_apps.enabled`, `blocking.native_apps.blacklist`,
    `blocking.browser_extension.enabled`. **Read that list; do not extend it.** This phase
    adds no editing capability: the set of editable fields is exactly what it is today.

    **`ControlRow(Static, can_focus=True)`**, with `classes="ctl"`:
      - `on_enter` → `self.focus()`. This is the whole shared-cursor mechanism. Do **not**
        add a `self._cursor_index` or any second cursor state — two models can disagree,
        one cannot.
      - `on_click` → activate. **The whole row is the click target**, which comes free from
        the row being the widget; no inner `Static` may swallow the click.
      - `Enter` and `Space` activate the focused row, which comes free with focus and matches
        `onReturnPressed` / `onEnterPressed` / `onSpacePressed` on every control in the kit.
      - `-pressed` toggled for the duration of the press, `-selected` and `-refused` set from
        the row model, via `set_class` / `toggle_class` on the widget — the house state
        mechanism (`status.py:263-269`).
      - A refused row activates to surfacing its own refusal string and nothing else. It
        must not push the edit screen.
      - Right-click is wired and **unused** in 12.1 — noted as the kit does with
        `PanelSlider.rightClicked()`, not invented. `Click.button` is 3 on right and
        `Click.chain` is 2 on double, both populated in 8.2.7.
      - `tooltip` set from the contract's tooltip copy where a row has one. Each tooltip says
        what the machine knows that the config cannot.
      - No bracket hints anywhere. No action may require a memorised key.

    **Colour reaches this widget as a role name, never a value** — the mechanism that makes
    the hex ban enforceable by a file scan. Control 1 is live and scanning
    `ngtui/ngtui/widgets/*.py`, and this file is now in its glob.

    Meaning never rides on colour alone: `on`/`off` reads as two reverse-video cells filled
    versus hollow, a refused row drops its value to the quiet channel **and** states the
    reason on the row, and an empty list reads as a gap rather than "nothing to show" —
    `no site is blocked` in the alarm role with the consequence spelled out beside it. `—`
    and "no items" are both wrong: the list being empty *is* the finding.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a control's activation → the edit surface | the point where a click becomes an intent to change signed config |
| the rendered row → the user's belief about what is editable | a refusal that reads like enforcement is the dangerous failure here |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12.1-15 | Elevation of Privilege | a row rendered "refused" being mistaken for enforcement | mitigate | **The named risk of this phase.** The row's `refusal` string is presentation only. The seam hands a `route` or a `refusal` to the *existing* edit surface, which still goes through `backend.commit()` and the signer's direction classifier and edit-window refusal. This plan adds **no** UI-side allow/deny decision — asserted by `grep -cE 'commit\|suspend\|sudo'` returning 0 in `controlrow.py`, and by `test_edit_window*.py` staying green untouched. |
| T-12.1-16 | Elevation of Privilege | a control committing before the signer's refusal is visible | mitigate | No control on the home surface commits anything. 12.1 changes no config and stages nothing; the only route to a commit is the `edit` chip opening the existing `EditScreen`, whose `ConfirmScreen` gate before a signed commit is unchanged. `tests/test_port02_commit_argv.py` and `tests/test_run_sudo_pty.py` are the standing controls. |
| T-12.1-17 | Spoofing | a stale or misreported row value | mitigate | Every row value is read through `backend`'s existing public reads at compose time, and the countdown stays the only tick-refreshed cell. No row caches a verdict or a token count across a repaint. |
| T-12.1-18 | Denial of Service | a click landing on nothing | mitigate | Control 6b clicks at several x positions across the row width including the far edge; a dead region in a control the user believes is live is how a late-night user concludes the app is broken and reaches for the raw config instead. |
| T-12.1-SC | Tampering | package installs | n/a | No package added, removed or upgraded. |
</threat_model>
