## The instrument as built

Four rows, `height: auto`, at the probe's measured width of **131**:

| Row | id | Content |
|---|---|---|
| 1 | `#ramp` | `" .:-=+*#%@"` by density, one `█` for now |
| 2 | `#permission` | `▔` where the **signed** edit window admits a loosening |
| 3 | `#hour-axis` | `00`, `02` … `22` |
| 4 | `#readout` | reserved; filled by either input |

```
screen Size(width=135, height=46) | hero region Region(x=1, y=1, width=133, height=4)
ramp content width 131
```

**131, not 120, 129 or 135.** The screen rule in `app.tcss` takes one column of frame
either side and the widget one more of padding: 135 − 2 − 2 = 131. This is the third
different "real" ramp width the phase has produced (RESEARCH said 129 from the column
budget, the plan's probe used 120, plan 05 measured 132 for a `.ctl` row), which is the
whole argument for the contract's "no literal ramp width in code" rule. Every column in the
widget and in the test is derived from `ramp.content_size.width` read at paint time.

### The greyscale ladder, as actually painted

Against the live desktop theme, whose resolved `foreground` is `#DADDFB`. Alpha is
`0.30 + 0.055 × d`, with the inside-the-curfew band pinned to `0.92` and the now marker at
full strength, bold:

| glyph | d | alpha | painted RGB |
|---|---|---|---|
| `.` | 1 | 0.355 | (77, 78, 89) |
| `:` | 2 | 0.410 | (89, 90, 102) |
| `-` | 3 | 0.465 | (101, 102, 116) |
| `=` | 4 | 0.520 | (113, 114, 130) |
| `+` | 5 | 0.575 | (125, 127, 144) |
| `*` | 6 | 0.630 | (137, 139, 158) |
| `#` | 7 | 0.685 | (149, 151, 171) |
| `%` | 8 | 0.740 | (161, 163, 185) |
| `@` | 9 | 0.92 | (200, 203, 230) |
| `█` | — | 1.00 bold | (218, 221, 251) |

Ten distinct values, monotonic — the alphas reached the compositor rather than collapsing
to one ink. **`d=1 → 0.355` is RESEARCH's own measured figure**, reproduced here on a
different foreground.

The gap between `%` (0.740) and `@` (0.92) is deliberate and is the one deviation from the
linear formula: the curfew is the band the eye must find without counting glyphs, and the
jump is what makes its edge read as an edge. Density still carries the whole meaning
without it — the ramp is identical with every colour stripped.

## The colour route taken, and why

**`textual.content.Content` + `textual.style.Style`, not `rich.text.Text`.**

RESEARCH's measurement is the reason and it is worth restating exactly, because the failure
it predicts is a crash at first paint rather than a wrong colour:

```
Color.parse("#a9c0bf").with_alpha(0.355).hex  ->  '#A9C0BF5A'      (eight digits)
rich.style.Style.parse('#a9c0bf5a')           ->  StyleSyntaxError:
    unable to parse '#a9c0bf5a' as color; '#a9c0bf5a' is not a valid color
```

The `Content` route never renders a colour to a string at all: the alpha rides on a
`Style` inside a `Span` and Textual's compositor blends it against the widget's real
background. So T-12.1-22 is not *avoided* here, it is structurally unreachable — there is
no code path in `hero.py` that could hand `rich` a hex.

```
$ grep -c 'rich.text'                 ngtui/ngtui/widgets/hero.py   -> 0
$ grep -cE '#[0-9a-fA-F]{8}'          ngtui/ngtui/widgets/hero.py   -> 0
```

The acceptance criterion's watch-for — a `StyleSyntaxError` at mount — never fired: the
widget mounts and paints in every one of the three controls and in four ad-hoc probes.

### Control 11b — the off-by-one mapping, and the measurement that changed the control

Armed by `i / width` instead of `(i + 0.5) / width` in `column_minute`, exactly as the plan
prescribes:

```
E   AssertionError: the ramp does not sample the day symmetrically — column 0 reads 00:00
    and the last column reads 23:49, 0 minutes from midnight versus 11. The
    column-to-minute mapping is reporting each column's left EDGE instead of its centre.
E   assert 11 <= 1
E    +  where 11 = abs((0 - (1440 - 1429)))
```

**The off-by-one column the `i / width` variant produces at the measured width: the curfew
edge moves from 117 to 118, and column 117 goes from `21:31` to `21:26`.**

**And this is where the plan's prescribed recipe turned out to be blind — measured, not
reasoned.** With the arm in place and only the symmetry assertion relaxed, the whole of the
rest of control 11b **passes**:

```
$ # column_minute armed with i/width, symmetry tolerance relaxed to 9999
$ pytest -q tests/test_dashboard_hero.py::test_hovering_a_column_reads_out_its_hour
.                                                                        [100%]
1 passed in 0.52s
```

The reason is structural and is prior-wave finding 10 in a new shape: every expectation in
the test — the edge column, the expected read-out string, the column before it — is
**computed from `column_minute`**, the function being armed. A uniformly-wrong mapping
stays self-consistent with expectations derived from it, so the edge simply moves from 117
to 118 and every assertion follows it there. Derivation is what stops the test hardcoding
107; it is also what makes it unable to see an off-by-one.

The symmetry assertion is the fix, and it is deliberately **not** a re-derivation of the
formula. It states a property the spec implies — the ramp samples the day by column
*centres*, so the first column sits the same distance in from midnight as the last one does
from the end of the day (`00:05` and `23:54`, five minutes and six). The left-edge form pins
column 0 at `00:00` exactly and leaves the last column a whole column short, and that
asymmetry is visible without knowing how either minute was computed.

### Control 11c — the keyboard given its own formatter

Armed by rewriting `action_readout_right` to build and write its own string instead of
routing through the single `readout()` call site:

E   AssertionError: the keyboard and the pointer write different read-outs for column 55 —
    they are two code paths, not one destination
E       keyboard: '10:10  open'
E       pointer:  '10:10   open · a loosening is allowed here'
E   assert '10:10  open' == '10:10   open... allowed here'

## Decisions Made

- **`density_index` takes an optional curfew END, and the plan's two-argument signature is
  the degradation rather than the normal case.** Hours-until-the-start genuinely cannot
  distinguish "inside an eight-hour curfew" from "eleven hours away" — inside the curfew the
  wrapped countdown is 960–1440 minutes, which the ladder reads as index 1. With no end the
  function marks only the start minute itself as inside rather than inventing a duration,
  and the widget always supplies both from the signed config. Both forms give exactly
  `{1..9}` over all 1440 minutes, which is what the plan's acceptance criterion asserts.
- **The now marker is painted only when the clock was verified.** `now_column(None, width)`
  returns `None` and the widget paints no marker. On a product whose entire premise is that
  the clock can be lied to, a marker is an assertion about what time it is; an unverified
  clock must produce no assertion rather than a plausible one. The clock comes from
  `backend.cache_only_now_minutes` — the existing non-blocking read the edit preview already
  uses, so the hero cannot hang the UI on a cold `.timecache`.
- **A malformed edit window refuses everywhere, a missing one allows everywhere.** Both
  mirror the signer's `_edit_window_refusal` exactly: it fails closed on unparseable bounds
  and gates nothing when the block is absent or disabled. The channel and the refusal the
  user actually meets cannot disagree (T-12.1-19).
- **Unparseable curfew bounds paint the quiet floor, not a guessed curfew.** The ramp fills
  with index 1 and the read-out says `open`, which is what the signed config actually
  supports. Inventing a curfew would be the TUI asserting a lock nobody signed.
- **The read-out starts on the now marker rather than empty or at column 0.** The reserved
  row is informative on arrival and `h`/`l` continue from where the instrument already
  points. It costs no reflow either way — the row is reserved whether or not it is filled —
  and with no verified clock it stays empty, which is the honest state.
- **`on_mouse_move` lives on `DayRamp`, not on the `#ramp` cell.** Input events bubble and
  all four cells share the widget's left edge, so hovering the permission channel reads out
  the same hour the ramp above it does. One instrument drawn in four rows should answer as
  one instrument.
- **`h`/`l` mirrored onto `left`/`right`, all `show=False`.** No bracket hint appears on
  this surface (OD-2) and `j`/`k` belong to the control walk, so the ramp takes the
  horizontal pair.

## Issues Encountered

**The measured ramp width is the third different number this phase has produced.** RESEARCH
derived 129 from the column budget, the de-risking probe used 120, plan 05 measured 132 for
a `.ctl` row, and the hero on a bare probe screen measures **131**. They are all correct for
their own composition. Nothing downstream should treat any of them as *the* ramp width —
plan 07's composition will produce a fourth, and the widget and both its tests read it at
paint time.

**`Static` has no `renderable` attribute in textual 8.2.7.** `AttributeError: 'Static'
object has no attribute 'renderable'. Did you mean: 'render_line'?` The accessors that exist
are `.content` (what was handed to `update()`) and `.render_line(n)` (what is painted). The
tests use `render_line(0).text`, which is the stronger of the two for a control asserting a
*destination*. Measured: the strip is **not** right-padded, so a byte-identical comparison
means what it says.

**`app.theme_variables["foreground"]` is a string, not a `Color`.** `Color.parse` is applied
at paint time. Reading it per repaint rather than caching it at construction is deliberate —
`refresh_css` on a desktop theme change re-lays-out the widget, which re-enters `_paint`,
so the ramp follows a live theme swap with no extra machinery.
