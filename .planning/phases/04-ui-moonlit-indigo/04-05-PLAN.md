<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| edit inputs (TS) → classify_change / commit_change | Untrusted edited YAML crosses into the authoritative classifier/committer |
| UI commit/+8 gates → Rust command gates | UI gates are advisory; the Rust commands re-enforce every gate |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-18 | Elevation of Privilege | UI bypasses the 0-token gate to force a loosen commit | mitigate | The UI disables Commit at 0 tokens (clarity), but plan-03 commit_change re-checks `decision.allowed` server-side (defense in depth, commit.rs:148) so a forced invoke is still refused. |
| T-04-19 | Spoofing | optimistic token decrement / grace flip before the command confirms | mitigate | After commit_change / use_grace the UI re-renders ONLY from the returned re-verified StateDto (D-09); no local token/grace mutation. |
| T-04-20 | Elevation of Privilege | +8 grants outside an active lock or when already used | mitigate | UI enables +8 only on `locked && grace_available_today`; use_grace (plan 03/engine) refuses NtpUnreachable / GraceAlreadyUsedToday regardless of UI state (fail-closed). |
| T-04-21 | Tampering | a loosening commit slips through without the user noticing the cost | mitigate | One explicit confirm step on loosening commits naming the token cost (D-08); tighten-only commits are free and unconfirmed. |
| T-04-22 | Repudiation | UI shows a commit succeeded when the engine rejected it | mitigate | Commit/grace errors surface inline and the displayed state stays the pre-action re-verified DTO; success path re-renders the returned StateDto. |
</threat_model>
