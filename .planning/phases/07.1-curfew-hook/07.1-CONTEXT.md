# Phase 07.1: Curfew Hook (Linux) - Context

**Gathered:** 2026-06-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Wire `guard.py` into Claude Code as the **curfew enforcement hook** on Linux (CURF-01). The
verdict engine already returns the correct verdict (`deny` in curfew, `allow` outside / in
grace) — this phase builds the missing **adapter + wiring** that fires it on a Claude Code
event and translates its verdict into the hook contract, so curfew actually blocks sessions.
The Linux equivalent of the retired Windows `nightguard_adapter.ps1`.

**In scope:** the adapter script, the verdict→hook-contract mapping, the global hook wiring
(via the LifeOS generator), and the curfew allowlist (slash-commands that pass during curfew).

**Out of scope (already done or other phases):** the curfew verdict engine itself (`guard.py`,
done); config-integrity/revert (Phase 7 root watchdog, done); browser block (StayFree policy,
done); native-app kill (Phase 8, NBLK-01). This phase adds **no new verdict logic** — only the
wiring that fires the existing engine.

</domain>

<decisions>
## Implementation Decisions

### Hook event
- **D-01:** Fire on **`UserPromptSubmit` only.** It is the only Claude Code event that can
  *hard-block* (exit 2 / block decision erases the prompt and shows the message). `SessionStart`
  **cannot deny** — it can only inject context — so it is not used. Mirrors the Windows adapter.
- **D-02:** The session may remain *open* during curfew; what is blocked is **sending prompts**.
  This deliberately preserves the ability to run allowlisted slash-commands (plan tomorrow,
  shutdown) — see D-09..D-11.

### Scope & survival
- **D-03:** Enforcement is **global** — every Claude Code session on the machine is curfew-gated,
  regardless of project directory. A late-night user must not be able to dodge curfew by opening
  Claude in an un-gated repo. (Rejected: per-project wiring.)
- **D-04:** The hook is **declared in LifeOS `config/` and emitted by the generator**
  (`scripts/sync/sync_agent_config.py`), so the wiring is reproducible on a fresh machine and
  survives SessionStart regeneration. (Rejected: hand-wiring `~/.claude/settings.json`.)
  - **Planner must resolve:** which managed settings file gives *global* reach. The generator
    today writes `~/.claude.json` and each project's `.claude/settings.local.json`, and does
    **not** currently manage `~/.claude/settings.json`. Global reach most likely means teaching
    the generator to emit the curfew hook into user-global `~/.claude/settings.json` (a file the
    generator does not touch today, so adding managed-emit there is new work). Confirm the exact
    target so the hook applies to all sessions, not just LifeOS/nightguard.
- **D-05:** The adapter script itself lives **git-tracked in `LifeOS/hooks/`** (e.g.
  `LifeOS/hooks/nightguard_adapter.py`), invoked by absolute path with `python3` (Linux
  interpreter rule from AGENT-SYSTEM.md — never relative paths / `powershell` / `C:\`).

### Deny contract
- **D-06:** Block via **exit 2 + butler message on stderr** (mirror `nightguard_adapter.ps1`).
  The prompt is erased and the message is surfaced to the user. (Rejected: JSON `{"decision":
  "block","reason":...}` — kept the battle-tested exit-2 path.)
- **D-07:** **Exit-code translation invariant (load-bearing):** the adapter must **translate**
  guard's `exit 1` (deny) into the hook's **exit 2** block. It must NOT propagate guard's exit
  code — a hook `exit 1` is a *non-blocking / fail-OPEN* error on this runtime. `guard.py`
  exit 0 = allow → adapter exit 0.
- **D-08:** **Fail-closed:** any error/exception in the adapter (unset/unresolvable
  `NIGHTGUARD_DIR`, guard throw/crash, unparseable verdict JSON, non-{0,1} guard exit) →
  **block (stderr + exit 2)**, never allow. Use the config `offline_message` (or a hardcoded
  fallback if config is unreadable).

### Adapter shape & message surfacing
- **D-09:** **Python adapter** (`nightguard_adapter.py`), reusing `ngcommon.py`'s `yaml_load` —
  keeps the "single Python stack" invariant. (Rejected: bash wrapper — would have to parse YAML
  for butler messages.) The adapter: runs `guard.py` in **soft mode** (no key) with
  `NIGHTGUARD_DIR` = the canonical LifeOS instance dir; reads the verdict JSON; on deny maps
  `reason → butler message` from `config.yaml` and emits exit 2 + stderr.
- **D-10:** **Butler-message mapping** comes entirely from `config.yaml` (single source of truth,
  no hardcoded strings except the fail-closed fallback):
  - `reason: curfew` → `curfew.message` with `{start}` / `{end}` substituted from the config window.
  - `reason: clock tamper` → `curfew.tamper_message`.
  - `reason: ntp unreachable` (and any other deny reason) → `curfew.offline_message` (fail-closed default).
  - UTF-8 output so the Spanish-butler ñ/accents render correctly.

### Curfew allowlist
- **D-11:** **Exact slash-command allowlist**, matched on the **leading token**. The adapter
  checks the prompt's first whitespace-delimited token against `config.yaml` `allow_commands`;
  on a match the prompt **passes with its arguments intact** (params ride along). Everything
  else during curfew is blocked. This is the only escape valve — deliberate, command-shaped,
  hard to abuse (rejected: prefix/substring match = easy curfew bypass; rejected: drop the
  allowlist and rely solely on grace).
- **D-12:** `/plan` must accept **free-form parameters** — e.g.
  `/plan tomorrow: finish watchdog tests at 09:00, then …` passes because the leading token is
  `/plan`; the rest is the planning spec and is allowed through. `/shutdown` passes the same way.
- **D-13:** The allowlist must work for **skill-backed slash commands**: when `/plan` invokes a
  planning *skill*, the hook sees the raw `/plan …` text and matches the leading token, covering
  both the command and the skill it triggers. The allowlist is config-driven, so adding/removing
  allowed commands is a `config.yaml` edit (signed like any config change).
  - **Planner must VERIFY on the runtime:** that `UserPromptSubmit` actually *fires* and exposes
    the `/plan …` text for skill-backed slash commands. Some built-in slash commands do not emit
    a prompt event — if `/plan` does not produce a `UserPromptSubmit` payload, the allowlist
    cannot see it and the escape valve fails. This is the top integration risk for this phase.

### Carried forward (LOCKED upstream — do not re-litigate)
- **Soft mode:** the user-context guard runs key-less (`read_key()==None`); curfew still
  evaluates; integrity remains the **root watchdog's** job. The hook does NOT need the key.
- **Canonical config:** read the LifeOS canonical instance (`NIGHTGUARD_DIR =
  /home/danitrrga/dev/Projects/LifeOS/nightguard`); no `~/.claude` drift (mirrors WIRE-01).
- **Grace:** outside curfew AND during an active daily grace window → allow. `guard.py` already
  reads `guard.json.grace` (user-readable 0644) and returns `allow / grace active`. No grace
  logic in the adapter.

### Claude's Discretion
- Adapter timeout value for the hook entry (Windows used ~20–25s on other hooks; keep short so
  a guard hang fails closed quickly rather than freezing the prompt).
- Whether/how to log curfew blocks (the guard already keeps an HMAC-chained audit; an extra
  adapter-level log line is optional — keep it lightweight if added).
- Exact `NIGHTGUARD_DIR` resolution inside the hook env (env may differ from an interactive
  shell; the adapter should resolve robustly, defaulting to the canonical path).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `guard.py` — invoked as-is (soft mode, `NIGHTGUARD_DIR` set). No change needed; it already
  emits the verdict + exit code and handles grace/NTP/clock-tamper.
- `ngcommon.py::yaml_load` — reuse to read `config.yaml` butler messages + `allow_commands` in
  the adapter (no second YAML parser).
- `config.yaml` butler fields (`curfew.message`/`tamper_message`/`offline_message`,
  `{start}`/`{end}`, `allow_commands`) — the single source of truth for all surfaced text.
- The Windows `nightguard_adapter.ps1` — direct logic template (exit mapping, message mapping,
  allowlist, fail-closed) to port to Python.

### Established Patterns
- **Single Python stack on Linux** (memory: `nightguard-linux-python-trust-stack`) — the adapter
  must be Python, reusing the existing primitives; do not introduce a parallel implementation.
- **Generated-files-are-regenerated** — never hand-edit `~/.claude/hooks` or project
  `settings.local.json`; wiring goes through LifeOS `config/` + the generator (D-04).
- **Fail-closed everywhere** — every ambiguity in the trust stack resolves to "block", never to
  a silent allow (mirrors guard/watchdog).

### Integration Points
- Claude Code `UserPromptSubmit` event → `python3 LifeOS/hooks/nightguard_adapter.py` → `guard.py`.
- The generator emits the hook entry into the global settings; the adapter resolves
  `NIGHTGUARD_DIR` to the canonical LifeOS instance dir.

</code_context>

<specifics>
## Specific Ideas

- The escape valve the user explicitly wants: be able to **plan tomorrow** and **shut down**
  during curfew. Realized as `allow_commands` = exact slash-commands (`/plan`, `/shutdown`),
  with `/plan` accepting free-form parameters describing what/when to do tomorrow, and working
  for the `/plan` skill. Everything else is blocked with the Spanish-butler message.
- Mirror the proven Windows adapter behavior 1:1 where possible — this is a *port*, not a redesign.

</specifics>
