# Phase 07.1: Curfew Hook (Linux) - Research

**Researched:** 2026-06-23
**Domain:** Claude Code hook integration (UserPromptSubmit) + Python adapter port + LifeOS generator/settings wiring
**Confidence:** HIGH on the hook contract and global-reach mechanism; MEDIUM on the exact `prompt`-field contents for slash commands (one runtime probe required — see Open Questions Q1).

## Summary

This is a **port, not a redesign**. The verdict engine (`guard.py`) is complete and verified
working in soft mode on this machine: outside curfew it returns `{"decision":"allow",...}` exit 0;
under a simulated curfew override it returns `{"decision":"deny","reason":"curfew",...}` exit 1.
What is missing is the **Linux adapter** that translates that verdict into the Claude Code
`UserPromptSubmit` hook contract, plus the **wiring** that fires it globally.

Two top risks were investigated and largely resolved:

1. **Does `UserPromptSubmit` fire and expose the `/plan …` text?** Per the official hooks docs,
   `UserPromptSubmit` fires for **every** submitted prompt including slash commands, *before*
   `UserPromptExpansion`, and the `prompt` field carries the user's submitted text. The remaining
   uncertainty is **what exact string** the `prompt` field holds for a slash command: live
   transcripts on this machine store the *expanded* form
   (`<command-name>/plan</command-name>\n<command-message>plan</command-message>\n<command-args>…</command-args>`),
   not a literal `/plan tomorrow …`. The retired Windows adapter sidestepped this with a
   **substring** match (`-match [regex]::Escape($cmd)`), which matches `/plan` anywhere in that
   blob. D-11's "leading-token only" rule may therefore **fail to match** the expanded form. This
   is the single item that needs a one-shot live probe before the matcher strategy is finalized
   (Open Question Q1 + Wave-0 probe task).

2. **Which file gives global reach (D-04)?** `~/.claude/settings.json` (user scope) is read for
   **every** Claude Code session regardless of project dir, and **hook arrays concatenate across
   scopes** (user + project + local all fire) — so a curfew hook there cannot be dodged by opening
   an un-gated repo. **Important correction to CONTEXT.md's assumption:** `sync_agent_config.py`
   does **not** manage hooks at all today (the `sanitize_hook_block`/`translate_hook_command`
   translators named in CONTEXT.md/canonical-refs **no longer exist** — they were deleted in the
   2026-06-22 single-agent purge). The AGENT-SYSTEM.md "Add/change a hook" row says hooks are wired
   by **editing `.claude/settings*.json` directly** with an absolute `python3` path. So D-04 is
   either (a) hand-wire `~/.claude/settings.json` once (it is *not* regenerated — the generator
   never writes it), or (b) teach `sync_agent_config.py` to manage a hooks block in
   `~/.claude/settings.json` as genuinely new work. See Open Question Q2.

**Primary recommendation:** Build `LifeOS/hooks/nightguard_adapter.py` as a near-1:1 Python port of
`nightguard_adapter.ps1` (reuse `ngcommon.yaml_load`; resolve `NIGHTGUARD_DIR` to the canonical
LifeOS instance with a hardcoded default; run `guard.py` via `subprocess`; translate guard exit
1→hook exit 2, guard exit 0→hook exit 0, everything-else→exit 2 fail-closed; map `reason`→butler
message from `config.yaml`; allowlist-check the prompt BEFORE invoking the guard). Wire it into
**`~/.claude/settings.json` `UserPromptSubmit`** with `timeout: 10`. Use a **substring** allowlist
match (mirroring the proven Windows adapter) unless the runtime probe confirms the raw `/plan …`
leading token is exposed — see Q1.

### Pattern 1: The hook stdin payload (UserPromptSubmit)
**What:** Claude Code pipes a JSON object on stdin; the prompt text is in the `prompt` key.
**When to use:** Always, at the top of `main()`.
```python
# Source: https://code.claude.com/docs/en/hooks  (UserPromptSubmit input schema)
# {
#   "session_id": "abc123",
#   "transcript_path": "/…/*.jsonl",
#   "cwd": "/…",
#   "permission_mode": "default",
#   "hook_event_name": "UserPromptSubmit",
#   "prompt": "the text the user submitted"
# }
import sys, json
raw = sys.stdin.read()
try:
    prompt = (json.loads(raw) or {}).get("prompt", "") or ""
except Exception:
    prompt = ""   # unparseable stdin is NOT fatal — proceed to guard, fail-closed downstream
```
Mirrors the working `guard_tool_use.py` pattern on this same runtime (`raw = sys.stdin.read();
payload = json.loads(raw)`). [VERIFIED: read of LifeOS/hooks/guard_tool_use.py]

### Pattern 2: The block contract (exit 2 + stderr)
**What:** To hard-block, write the butler message to **stderr** and `sys.exit(2)`. Exit 0 = allow,
emit nothing. **Never exit 1** — exit 1 is a *non-blocking* error on this runtime (fails OPEN).
```python
# Source: https://code.claude.com/docs/en/hooks (Exit code 2: "Blocks prompt processing and
#         erases the prompt"); confirmed by working guard_tool_use.py deny()
def send_block(msg, fallback="Nightguard is unavailable. For your own good, the house remains closed."):
    sys.stderr.write((msg or fallback) + "\n")
    sys.exit(2)
```
[VERIFIED: code.claude.com/docs/en/hooks exit-code table] + [VERIFIED: guard_tool_use.py `deny()`
does exactly `sys.stderr.write(...); sys.exit(2)`]

### Pattern 3: Invoke the guard oracle, isolate its exit code
```python
# Source: port of nightguard_adapter.ps1 "& powershell.exe -File $guardScript; $guardExit = $LASTEXITCODE"
import os, subprocess
env = dict(os.environ); env["NIGHTGUARD_DIR"] = data_dir
guard_py = os.path.join(os.path.dirname(__file__), "..", "scripts", "nightguard", "guard.py")
p = subprocess.run([sys.executable, guard_py], capture_output=True, text=True, env=env, timeout=8)
guard_exit = p.returncode           # 0 allow / 1 deny / other = crash → fail-closed
verdict = {}
try:
    verdict = json.loads(p.stdout.strip().splitlines()[-1])   # guard prints one JSON line
except Exception:
    verdict = {}                    # unparseable verdict on a deny → fail-closed offline_message
```
Note: `guard.py` lives in `LifeOS/scripts/nightguard/`, **not** beside the adapter (the PS version
had the guard as a sibling). Resolve the path explicitly. [VERIFIED: ls of both dirs]

### Pattern 4: UTF-8 output for the Spanish butler
The butler strings contain `ñ`/accents (`Mi señor…`). Python 3 stdout/stderr default to UTF-8 on
Linux, but be explicit if the hook env sets `LANG=C`. The PS adapter forced
`[Console]::OutputEncoding = UTF8`; the Python equivalent is to ensure the stream is UTF-8:
```python
sys.stderr.reconfigure(encoding="utf-8")   # Python 3.7+; guards against a C locale in the hook env
```
[ASSUMED] — the hook env locale is unverified; reconfigure is a cheap safety net (D-10 requires the ñ to render).

### Anti-Patterns to Avoid
- **Propagating `guard.py`'s exit code.** Guard exit 1 piped straight through = hook exit 1 =
  **fail-OPEN** (prompt passes during curfew). The adapter MUST translate 1→2. This is the
  load-bearing invariant (D-07).
- **Any code path that can reach an implicit exit 0 on error.** Every error branch must
  `send_block(...)` (exit 2). The PS adapter even has a terminal defensive `Send-Block` after the
  try/catch — port that belt-and-suspenders fall-through.
- **Hardcoding butler strings.** All text comes from `config.yaml` except the single fail-closed
  fallback used when the config itself is unreadable (D-10).
- **Leading-token match assumed without a runtime probe.** See Q1 — the expanded slash-command
  form may break it.
- **Wiring the hook into a project `settings.local.json`** (e.g. nightguard-control's) — that is
  per-project and dodgeable, and is also generator-managed/overwritten. Global reach requires
  `~/.claude/settings.json` (D-03/D-04).

## Common Pitfalls

### Pitfall 1: Fail-OPEN via exit 1 (the cardinal sin)
**What goes wrong:** Adapter returns guard's exit 1, or hits an unhandled exception that exits
non-2; the prompt passes during curfew.
**Why it happens:** Naive `sys.exit(guard_exit)` or letting a traceback propagate (Python exits 1
on uncaught exception).
**How to avoid:** Wrap `main()` in a top-level `try/except` whose `except` calls `send_block(...)`
(exit 2). Translate guard exit codes explicitly: `0→0`, `1→2(map reason)`, `else→2(offline)`. Add a
terminal `send_block()` after the try block as a defensive fall-through (port the PS pattern).
**Warning signs:** A curfew-time prompt is NOT blocked; `echo $?` after a manual run of the adapter
with a deny verdict shows anything other than 2.

### Pitfall 2: The allowlist never matches the slash command
**What goes wrong:** `/plan` is blocked during curfew despite being in `allow_commands`.
**Why it happens:** The `UserPromptSubmit` `prompt` field for a slash command may be the **expanded**
blob (`<command-name>/plan</command-name>…`), so a strict leading-token equality test
(`prompt.split()[0] == "/plan"`) fails — the first token is `<command-name>/plan</command-name>`.
**How to avoid:** Resolve Q1 with a live probe. Until then, mirror the Windows adapter's **substring**
match (`any(cmd in prompt for cmd in allow_commands)`), which matches `/plan` wherever it appears. If
the probe shows the raw `/plan …` text IS exposed, the safer leading-token rule (D-11) can be used.
**Warning signs:** Probe log shows `prompt` containing `<command-name>` tags.

### Pitfall 3: NIGHTGUARD_DIR unset in the hook env → wrong/empty config
**What goes wrong:** The hook process doesn't inherit the env var; `ngcommon` falls back to its own
default, or the adapter throws.
**Why it happens:** Claude Code hook subprocesses don't necessarily carry interactive-shell exports.
**How to avoid:** The adapter hardcodes the canonical default
`/home/danitrrga/dev/Projects/LifeOS/nightguard` when `NIGHTGUARD_DIR` is unset, and passes it
explicitly into the guard subprocess env. (Note: `ngcommon` already defaults to `ROOT/nightguard`,
which resolves to the same canonical dir since guard.py lives under LifeOS — but be explicit; don't
rely on cwd.) [VERIFIED: ngcommon.py line 20]
**Warning signs:** Adapter reads an empty/short config; offline_message fires unexpectedly.

### Pitfall 4: Project-scope hook REPLACING the global one
**What goes wrong:** Belief that a project's `.claude/settings.json` UserPromptSubmit would override
the global curfew hook, letting the user dodge curfew in that project.
**Reality (resolved):** Claude Code **concatenates hook arrays across scopes** — user + project +
local hooks all fire. The global curfew hook is therefore present in every session. [VERIFIED:
code.claude.com/docs/en/settings + GitHub issue anthropics/claude-code#11392 "merges instead of
overriding hooks"]
**Residual bypass to note (not block):** `disableAllHooks: true` in any settings scope turns off ALL
hooks. A determined late-night user could set it — but that is an out-of-band config edit of the same
character as disabling the watchdog, and arguably belongs to a future hardening note, not this phase.

### Pitfall 5: Editing config.yaml by hand to add /plan
**What goes wrong:** Raw edit of `config.yaml` to add `/plan` is reverted by the root watchdog
within ≤60s (unsigned change), and the allowlist silently loses `/plan`.
**How to avoid:** Add `/plan` via the **control CLI commit path** (signs the config), per the Phase-7
integrity model. [VERIFIED: guard.py `verify_and_revert` + ROADMAP Phase 7]
