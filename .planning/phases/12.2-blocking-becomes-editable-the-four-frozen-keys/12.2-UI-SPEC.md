# Phase 12.2 — UI Design Contract

> A **delta** on the Phase 12.1 contract, not a replacement. Everything in
> `../12.1-native-dashboard-pointer-first-omarchy-tui/12.1-UI-SPEC.md` still holds — the
> token pipeline, the spacing scale in cells, the type mapping, the colour roles and accent
> reserve, the paint-priority ladder, the timings, the device frame, the hero, the
> accessibility rule. This document specifies only what 12.2 adds, and it is deliberately
> short because 12.1 left the seam.

---

## 1. What this phase changes, in one table

Four rows on the home surface stop being refusals and become routes. That is the whole
change to the existing composition.

| Cursor stop (12.1 §8.6) | 12.1 | 12.2 |
|---|---|---|
| 5 · `mode  blocklist ▏allowlist` | `refusal` | `route` → segmented control, staged in place |
| 7 · `always allowed` | `refusal` | `route` → the list editor |
| 8 · `game blocking` | `refusal` | `route` → switch, staged in place |
| 10 · `blocked sites` | `refusal` | `route` → the list editor |

The `ControlRow(label, value, detail, route | refusal)` signature does not change. The
ladder does not change. The cursor order does not change — it is still 16 stops. **If this
phase needs to touch the row widget, the seam was wrong and that is a finding, not a
licence.**

Two things are added: a **staged tray** on the home surface (§4) and a **list editor**
surface (§3).

## 2. The cost contract

### 2.1 The rule

A commit that touches a list costs **one token per list touched**, gated by the same clock
edit window that already gates a curfew loosening. Two lists in one commit is two tokens.
Per list, not per entry; per commit, not per keystroke.

The three lists that can be touched: the app blocklist, the app allowlist, the site list.
The two scalars (`mode`, `block_games`) keep the signer's existing polarity — loosening
costs one, tightening is free.

### 2.2 ⚠ Open decision — blocks one task, not the phase

**Does the per-list token apply in both directions, or only when the edit loosens?**

| | Rule | Consequence |
|---|---|---|
| **A** — as originally stated | any list touched = 1 token, window required, either direction | **you cannot tighten a list outside the window.** Adding `discord.com` to the site list is a tightening; under A it costs a token and is refused at 22:00 |
| **B** — recommended | 1 token + window only when the edit *loosens* (removing from a blocklist, adding to an allowlist). Pure additions to a blocklist are free at any hour | a midnight "take steam off, put it back tomorrow" is two commits and only the first is charged — a smaller loophole than it looks, but not zero |

Both are live behind a toolbar switch in `.planning/sketches/004-native-dashboard/`.

**Recommendation: B.** The product exists so the impulsive version of the user cannot
loosen the pact. Rule A also stops the disciplined version tightening it, and it
contradicts the rule the guard already applies to every other tightening — which would make
the one inconsistency in the system live exactly where the user is trying to do the right
thing.

**Rule B is also the smaller and safer change, which is evidence rather than preference.**
The early return at `nightguard_ctl.py:445` —

```
if not is_loosening(dirs):
    return dict(allowed=True, costs_token=False, ...)
```

— *is* the "tightening is always allowed, at any hour, and free" invariant, the oldest
guarantee in the system. Rule B leaves that line untouched and only adds a count to the path
that already charges, so it cannot regress the invariant. Rule A requires that early return
to become conditional on whether a list was touched: it is the riskiest line in the file to
modify, and getting it wrong silently makes tightening cost, or silently makes loosening
free.

**What this actually blocks.** Not the phase's planning — only the one signer-side task and
the copy in §5. Everything else (the list editor surface, the staged tray, the four routes,
the machine-knowledge disclosures) is identical under either rule and can be planned and
built now. Recorded this way rather than as a blanket blocker, because the rule is the
user's to set and he stated A; the argument for B is on record and waiting, not applied.

### 2.3 Where the rule lives — not negotiable

In the **signer's own quota decision** (`scripts/linux/nightguard_ctl.py`, the function both
`quota_decide` and the pre-authentication preview call). Not in the TUI.

That placement is the whole reason the refusal is visible before authenticating rather than
after — it is the same placement that already makes the edit-window refusal pre-auth, and
the hardening record says so explicitly: *"The gate sits in the quota decision, which is the
one function both the root signer and the pre-auth preview call. That placement is what
makes the refusal visible before you authenticate rather than after."*

The TUI reads the decision and renders it. It never computes a cost of its own. A TUI that
computed the cost itself would show a number the signer might disagree with, and the first
time they diverged the user would meet a prompt he could not pass.

### 2.4 What the signer change actually is — traced, not guessed

`quota_decide` (`scripts/linux/nightguard_ctl.py:423`) is confirmed to be the shared
function: `cmd_commit` calls it at line 541, and the terminal UI's pre-authentication
preview calls **the same function** by importing it (`ngtui/ngtui/backend.py:216`). So a
charge added there is visible pre-auth for free, with no second code path to keep in sync.

**It returns a boolean, not a count.** The charge is applied in exactly one place:

```
nightguard_ctl.py:553
weekly_spent = decision["effective_spent"] + (1 if decision["costs_token"] else 0)
```

`costs_token` has five consumers: that charge, the audit gate (555), the audit detail
(557-558), the CLI's own result line (562), and the terminal UI's preview copy
(`widgets/edit.py:163`). So the change is: `quota_decide` gains `token_cost: int`, and
`costs_token` is kept as `token_cost > 0` so the other four consumers are untouched.

**A bug this phase would otherwise introduce.** The quota ceiling is checked as
`if effective_spent < WEEKLY_TOKENS:` (line 453) — that is *"do you have any token left"*.
With N-token commits it must become *"do you have N left"*. Otherwise a 3-token commit
succeeds with one token remaining and drives `weekly_spent` to 4, past the ceiling, with no
refusal — and nobody would see it until the week a multi-list commit happened to be
affordable by exactly one. This is verification row 12 (§7).

## 3. The list editor surface

One surface, three lists, switched by a chip strip. Reached from cursor stops 7 and 10, and
from the existing `edit` chip.

**The focal point is the entries region**, and it is the only region that flexes. 12.1's home
surface anchors on the day ramp; this surface has no hero and should not borrow one — the
question it answers is "what is in this list, and what would changing it cost", so the
entries carry the eye and everything else is apparatus around them. Reading order is
top-down and deliberate: *which list* (row 5) → *what is in it* (rows 10–31) → *what to add*
(rows 34–39) → *what it costs* (row 42) → *what to do* (row 44). The cost line sits
immediately above the actions on purpose: it is the last thing read before anything is
authorised.

| 2 | 1 | header — identical to the home surface (§12.1 §7.2 row 2) |
| 3 | 1 | keyline |

| 6 | 1 | keyline |
| 7 | 1 | blank |
| 8 | 1 | label = the list's name · right: `click an entry to strike it` |
| 9 | 1 | blank |
| 10–31 | **1fr**, min 6 | the entries, one `ControlRow` each, `overflow-y: auto` |
| 32 | 1 | blank |
| 33 | 1 | keyline |
| 34 | 1 | label `A D D` |
| 35 | 1 | blank |
| 36 | 1 | the add field (`Input`, one row, no border box — `vkey` edges only) |
| 37 | 1 | blank |

| 39 | 1 | suggestion chips |

| 44 | 1 | action chip strip: `back` · `commit N tokens` · `discard this list` · `quit`. The discard chip drops **staged** edits only — nothing is written until commit — so it takes no confirmation dialog, but it carries the `warning` role and its tooltip names what it will drop: `drops N staged changes to this list · nothing signed is touched` |
| 45 | 1 | advisory: `the guard re-checks the hour with its own time source` |

**Fixed rows: 24. Entries region at 135 × 46: 22 rows. Minimum: 6.** The site list is the
one that grows, and 22 visible entries before scrolling is more than the product will
plausibly hold.

### 3.2 An entry is a control row

Same widget, same ladder, same whole-row click target. Per entry:

`▣ name  ·  state tag  ·  what the machine knows  ·  direction`

| Part | Rule |
|---|---|
| checkbox | `▣` kept, `▢` struck — glyph carries it, never colour alone |
| name | struck entries render with `text-style: strike` **and** dropped to the dim level; kept entries at full |
| state tag | `ADDED` or `STRUCK` — reverse-video tag, absent when unchanged. **Both carry the `staged` rung's `$warning`**, not the accent |
| knowledge | §3.3 |
| direction | `loosens` / `tightens`, right-aligned, dim — the signer's classification, never the TUI's guess |

**Why both staged states share one colour.** An earlier draft gave `ADDED` the accent. That
was wrong twice over. The accent reserve inherited from 12.1 §6.2 is closed at exactly two
uses — the wordmark dot, and the verdict word in `GRACE` — and a state tag in a list editor
is neither; that reserve is what keeps accent coverage under the 5 % the
`industrial-brutalist-ui` guardrail requires. And 12.1 §8.3 already has a rung for exactly
this meaning: a staged control borders in `$warning`. Added and struck are **one** meaning —
*staged, not yet signed* — so they take one colour, and the difference between them is
carried where the accessibility rule says it must be: the checkbox glyph, the word, and the
strike. Three channels, none of them colour.

Activating toggles struck ↔ kept, or removes a staged addition outright. **Nothing is
written.** The editor stages; only the signer commits.

### 3.3 What the surface shows that the config cannot (BLK-03)

This is the difference between a control panel and a config file with a cursor. Every one of
these is already known to the running system and is simply never surfaced:

| Shown | Source | Copy |
|---|---|---|
| an entry matches a running process | `appblock.matches_identity` on `/proc` `exe` | `matches /usr/lib/steam/steam` |
| an entry matches **nothing** | the same, empty | `matches nothing on this machine` (alarm role) |
| why it matches nothing, and the way out | known for the webapp case | tooltip: `a chromium webapp — shares one process with the calendar, the todo list and the portal` + `block it as a site instead: the site list reaches it, an app kill does not` |
| identity is not forgeable | `appblock` matches on `exe`, not `comm` | tooltip: `identity is read from the kernel's own exe path, never from comm, which is forgeable` |
| the titles game blocking would cover | `appblock.build_catalog` — Steam appmanifests, Heroic installed files, `Categories=Game` | tooltip lists them by name and where each was found |
| the floor the allowlist cannot shrink | `appblock.FLOOR_*` | `a floor protects the compositor, the shell, the portals, pipewire, the keyring and every terminal — config cannot shrink it` |
| enforcement is strong or weak | the watchdog's own tick | already on the home surface (12.1 stop 11) |

`discord` is the worked example and it must be visible without hunting: it has sat in the
app blocklist since June, it matches nothing, and the layer that can reach it is the site
list — which is one of the four keys this phase unfreezes.

### 3.4 Suggestions — the app offers what it knows

| List being edited | Suggestion row |
|---|---|
| site list | the entries the **app** layer cannot reach. `discord.com` first, because a blocklist entry for it already exists and does nothing |
| app blocklist | the installed titles the catalogue found, each with where it was found, and a note that turning game blocking on covers them all without naming any |
| allowlist | no suggestions — instead, the floor, stated. Suggesting additions to an allowlist would be suggesting a loosening, and the product does not do that |

**The allowlist row is the rule, not an omission.** The surface may suggest a tightening. It
must never suggest a loosening.

## 4. The staged tray on the home surface

12.1 deliberately draws no tray, because nothing could be staged from that surface and a
permanent "nothing staged" row would be a lie. 12.2 adds it, and **only when something is
staged** — it takes the 3 rows of ledger slack the 12.1 budget reserved (§12.1 §7.2),
leaving the ledger at its 4-row minimum.

| Rows | Content |
|---|---|
| 1 | hairline `▔` |
| 2 | `S T A G E D` + the list of touched things · right: `N tokens` (alarm role when N > tokens left) |
| 3 | blank |

The token meter in the band gains a third state: **spent** (dim), **available** (full), and
**about to be spent** (warning role) for the cells this commit would consume. That is the
whole cost, visible on the resting surface without opening anything.

## 5. Copywriting

### 5.1 Costs, stated the same way everywhere

| Case | Copy |
|---|---|
| a list is changed | `this list is changed — 1 token` |
| a list is unchanged | `this list is unchanged — 0 tokens` |
| the rule, under B | `one token only when the edit loosens; a pure addition is free` |
| the rule, under A | `one token per list touched, per commit — either direction` |
| running total | `N staged in total · M left this week` |
| over budget | `costs N tokens, M left this week` (alarm role) |

### 5.2 Refusals — the signer's words, never a guess

Inherits 12.1 §10.6 verbatim. Two cases are added:

| Case | Copy |
|---|---|
| window shut, list edit staged | `a change to a list is only accepted between 05:30 and 14:00 · checked before any prompt, never after` |
| over budget | `costs N tokens, M left this week · resets Mon YYYY-MM-DD` |

Both are shown **on the control, before it is activated** — not on the way back from a
failed authentication. The bounds come from the signed config and its signed timezone, not
the system clock.

### 5.3 Empty states read as gaps

| State | Copy |
|---|---|
| the site list is empty | `no site is blocked` (alarm role) + quiet: `the browser policy has nothing to enforce` |
| the allowlist is empty in allowlist mode | `every unnamed app would end` (alarm role) — this is the dangerous empty, and it must not read as tidy |
| no suggestions left | `nothing left to suggest` |

## 6. Accessibility

Inherits 12.1 §11 unchanged. The additions that must honour it:

| Element | Glyph | Word | Colour |
|---|---|---|---|
| kept entry | `▣` | — | full |
| struck entry | `▢` + strike | `STRUCK` | warning |
| staged addition | `▣` | `ADDED` | warning |
| over budget | `▲` | `costs N tokens, M left` | alarm |
| a list that costs | `●` | `1 token` | warning |
| a change that is free | `●` | `free` | dim |

A struck entry is legible as struck with colour off, because the checkbox glyph changes and
the text carries a strike — two channels, neither of them colour.

## 7. Verification — every assertion with its negative control

A check never seen to fail is not evidence. Each row names how it was proved able to fail.

| # | Assertion | Negative control |
|---|---|---|
| 1 | each of the four keys commits end-to-end through the signer against the **running** stack | a build with the key absent from the signer's field table commits it as a free no-op — the test sees zero token charge and fails |
| 2 | a commit touching N lists is charged N tokens, decided by the signer | stage two lists, assert the charge is 2; a per-commit-flat implementation charges 1 and fails |
| 3 | the cost is visible **before** authentication | assert the preview path returns the cost without invoking `sudo`; an implementation that charges only in `commit` returns no cost and fails |
| 4 | outside the window, a list edit is refused **by the signer**, with its own reason | neuter the hour comparison — the refusal disappears and the test fails (the same control the hardening session used for the edit window) |
| 5 | the refusal string the TUI shows is the signer's, verbatim | make the signer emit a distinctive reason; assert it appears unaltered. A TUI that composes its own text shows the composed one and fails |
| 6 | blocking a site is possible for the first time | commit a non-empty site list; assert the managed browser policy the watchdog writes contains it |
| 7 | the watchdog still reverts a hand edit to each of the four keys | hand-edit each, wait a tick, assert reverted. A build that drops one from the signed span leaves it standing and fails |
| 8 | the TUI still holds no key and computes no HMAC | the existing grep gate (`tests/test_port03_no_crypto.py`) — add the four new code paths to its span |
| 9 | the 46-row budget still holds with the tray drawn | the overflow control from 12.1, with something staged; the ledger at its 4-row minimum |
| 10 | an entry that matches nothing says so | fixture with an entry no `/proc` entry matches; assert the alarm copy. A build that renders every entry identically fails |
| 11 | the surface never suggests a loosening | assert the allowlist editor offers no suggestion chips; a build that suggests additions there fails |
| 12 | the weekly ceiling holds for an N-token commit | stage three lists with one token left, assert the refusal. An implementation that keeps `effective_spent < WEEKLY_TOKENS` allows it and drives the count past the ceiling — it fails |
| 13 | game blocking names the titles the catalogue found | fixture with two detectable installs; assert both names appear. A build that renders a bare boolean shows neither and fails |
| 14 | the allowlist floor is stated, and stated correctly | assert the copy lists the protected set from `appblock.FLOOR_*` rather than a hardcoded sentence; a build with a drifted literal fails when the floor changes |

Row 1 is the one that matters most, and it is the one that cannot be unit-tested: it is a
real commit against the live signer, which is a human-verified checkpoint.

## 8. Out of scope

| Item | Reason |
|---|---|
| The trust path's shape — `backend.commit()`, the inline `sudo` under `App.suspend()` with a real PTY, the direction classifier, the refusal to accept a weakening keystroke outside the window | Untouched in kind. The *only* signer change is the per-list charge inside the existing quota decision |
