# Phase 12.2 — Context

## The decision, in the user's own words

> "Deberían también editarle las cuatro llaves que hoy no se pueden tocar. O sea, sería
> lo suyo que mientras que estás en el periodo donde se puede editar el curfew, también
> puedes editar lo que son las listas y tal, también gastando un token. Por lista que
> quieres editar. Y por vez."

Read as:

1. The four blocking keys that cannot be reached today become editable.
2. They are editable **inside the same clock window** that already gates a curfew
   loosening — not a second, separate window.
3. Editing a list **costs a token**.
4. The charge is **per list touched, per commit** — not per entry, and not once for the
   whole commit. Two lists in one commit is two tokens.

## Why these four keys are the phase

The signer classifies eight blocking keys (`scripts/linux/nightguard_ctl.py:44-66`). The
only sanctioned editor exposes four (`ngtui/ngtui/widgets/edit.py:216`). The other four
were never wired:

| Key | Live value | Consequence today |
|---|---|---|
| `blocking.browser_extension.blocked_urls` | `[]` | **no site is blocked at all**, while the StayFree extension is force-installed and the watchdog restores the managed policy every tick |
| `blocking.native_apps.mode` | `blocklist` | allowlist mode is implemented and tested, and cannot be turned on |
| `blocking.native_apps.block_games` | `false` | Counter-Strike 2, Yu-Gi-Oh! Master Duel and Rocket League are installed and detectable, and are covered by nothing |
| `blocking.native_apps.allowlist` | `[zen-bin, foot]` | frozen |

They are not merely unexposed — they are **unchangeable**. A hand edit to `config.yaml`
is reverted by the watchdog, and the TUI is the only sanctioned writer. So the product
currently shows a blocking configuration it gives you no way to correct.

Related, and visible on the same surface: `discord` has sat in the native blocklist since
June and matches nothing, because it is a chromium webapp sharing one process with the
calendar, the todo list and the portal. The app-kill layer cannot reach it; the site list
can, and the site list is one of the four frozen keys.

## Open decision — must be resolved before planning

**Does the per-list token apply in both directions, or only when the edit loosens?**

Applied uniformly, as specified, *adding* a site to the blocklist is a **tightening** that
still costs a token and is still refused outside the clock window. So at 22:00, realising
you should block a site, you cannot make the pact stricter. That contradicts the rule the
guard already applies everywhere else: tightening is free and allowed at any hour.

| Option | Rule | What it costs |
|---|---|---|
| **A — as specified** | any list touched = 1 token, window required, either direction | you cannot tighten a list outside the window |
| **B — loosening only** | 1 token + window only when the edit loosens (removing from a blocklist, adding to an allowlist); pure additions to a blocklist are free at any hour | a midnight "take steam off, put it back tomorrow" is two commits and only the first is charged — a smaller loophole than it looks, but not zero |

Both are live behind a toolbar switch in `.planning/sketches/004-native-dashboard/` so the
difference can be felt rather than argued. **Recommendation: B**, because the product's
whole purpose is that the impulsive version of the user cannot loosen the pact, and option
A also stops the disciplined version tightening it.

## Constraints carried in

- **The signer decides, not the TUI.** The cost rule belongs in the signer's own quota
  decision — the one function both the pre-authentication preview and the commit call — so
  the cost and any refusal are visible *before* the fingerprint prompt and never after.
  That placement is what already makes the edit-window refusal visible pre-auth.
- **The TUI holds no key and computes no HMAC.** It stages; only the signer writes.
- **Do not add a key the classifier does not know.** A key absent from the field table
  commits as a free no-op, which is a silent bypass. All four are already in the table —
  that is precisely why this phase is small.
- **The watchdog must still revert a hand edit** to any of the four.
- Depends on Phase 12.1 for the control rows and the staging surface these are edited
  through.

## What the surface must show, beyond the values

The dashboard should offer what the machine already knows and the config cannot say:

- which blocklist entries match a running process, and which match nothing
- the titles the game catalogue detected, so game blocking is not a bare boolean
- the hardcoded floor the allowlist cannot shrink (compositor, shell, portals, pipewire,
  keyring, and every terminal — killing terminals would make the curfew unappealable)
- whether enforcement is the strong root-owned cgroup jail or the weak `SIGTERM` fallback
- for an entry the app layer cannot reach, the suggestion to block it as a site instead

`panel.py:232` picks `surface` from `lighter_background` or `selection`. Of the 28 installed

surface falls back to everforest's grey. In an ANSI palette the "lighter background" role is
`color8`, which dos-moos does declare (`#3A4849`). Fixing it is one name in the pick chain,
but it changes the appearance of the bar panel the user asked not to touch — so it is left
as his call rather than applied.
