# Milestone v2.0 · Linux Port — Audit

**Status: `gaps_found`** — the Linux trust spine (key → watchdog → signer → CLI → TUI) is wired and working end-to-end for the curfew/config-integrity path, but two blockers and five unsatisfied requirements need resolution before the milestone can be honestly closed.

## What works (the load-bearing spine)

The unifying primitive — **one root key → one root watchdog → one signer (control-CLI via sudo) → one schema → one HMAC** — is genuinely wired:

- **Phase 6 (LXCF-01/02):** the Linux `blocking.{browser_extension,native_apps}` schema flows consistently through the Python signer, the guard, and the Phase-10 TUI editable surface. Round-trip-proven.
- **Phase 7 (ROOT-01/03/04):** root-owned `.guardkey` (0600) + sanctioned config; the TUI commits only via the exact sudoers argv; hand-forging is infeasible.
- **Phase 7.1 (CURF-01):** `guard.py` is live as the Claude Code curfew hook (generator-owned in `~/.claude/settings.json`); a `deny` verdict blocks the session; allowlist + exit-code translation correct.
- **Phase 10 (PORT-01/03):** the omarchy Textual thin client reads state, previews via the signer's own classifier, signs via sudo, holds no key. 56 tests, ASVS-L1 secured, Nyquist-compliant.
- **E2E Flow B (hand-edit → revert):** COMPLETE — watchdog reverts tampered `config.yaml` to sanctioned within 60s, skipping the legitimate in-app write window.

## Blockers (must resolve before close)

### B1 — `guard.curfew_verdict` is uncommitted in LifeOS (affects PORT-02, NBLK-02)
Phase 10's `backend.live_verdict()` calls `guard.curfew_verdict()`, which exists **only as a 198-line uncommitted working-tree diff** in the LifeOS `guard.py`. Git HEAD (`3e64c81`, the Phase-8 revert) has no such function. A `git restore` or a fresh deploy would break the TUI's status display at import time. **Fix:** commit a standalone `curfew_verdict()` to LifeOS (decoupled from the reverted native-kill scaffolding) — it's a clean, key-less, pure verdict extractor the TUI legitimately needs.

### B2 — NBLK-01/02/03 marked Complete while the native-kill code was reverted (affects NBLK-01/02/03)
The Phase-8 Hyprland window-kill was committed then reverted (LifeOS `3e64c81`); the live watchdog has no kill logic. Yet `REQUIREMENTS.md` marks all three `[x] Complete`, the ROADMAP Phase-8 goal still claims the kill, and the Phase-8 SUMMARYs claim the requirements — and Phase 8 has **no VERIFICATION.md**. The tracking misrepresents what shipped. **Fix:** mark NBLK-01/02/03 descoped in REQUIREMENTS.md, update the ROADMAP Phase-8 goal, and add a descope note to `08-02-SUMMARY.md`. (The descope itself was a conscious user decision — "the curfew layer is sufficient"; only the bookkeeping is wrong.)
